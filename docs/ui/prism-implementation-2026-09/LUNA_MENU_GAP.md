# Luna 菜单还原专项审计与最小实施方案

> 审计日期：2026-09-15
> 审计范围：Prism 02「晴空棱镜」外壳中的侧栏分组、分组弹出菜单、菜单状态、图标、提示、顶部菜单入口及其与现有导航的衔接
> 审计基线：`ui/prism-v1`，HEAD `1545e0c7459f3d79eea302bdcee6b513bd12ee41`
> 工作树说明：`resources/build_info.json` 的修改及 `scripts/*_report.txt` 阶段报告属于既有工作树内容，本审计没有修改、暂存或清理。

## 结论先行

当前用户反馈的“实际软件里菜单、模块打开后的 Tab、顶部按钮缺失”，与原型代码的差异可以从源代码中复现为明确的 UI 缺口：

1. 原型侧栏是“首页 + 分组按钮 + 分组弹出菜单 + 设置/悬浮工具栏”，点击分组按钮打开玻璃弹层；当前 Vue 侧栏是分组标题下的常驻列表，当前原生侧栏也是常驻列表，二者都没有原型的分组弹层。
2. 原型默认外侧栏收起，当前 Vue 父分组默认全部展开，当前原生数据库和模型子分组默认按用户偏好打开；收起后的显示形态、分隔线和分组激活态因此不同。
3. 原型为每个分组提供独立图标、父分组状态和叶子入口；当前图标大部分已有本地映射，但“模型”父项当前使用 `chat`，原型分组使用 `spark`，是可见的图标差异。
4. 原型弹层会根据侧栏按钮位置进行四边约束，支持键盘焦点；当前 Vue/原生侧栏没有这一层，窄屏只把现有行缩成图标，无法以弹层访问完整子项。
5. 原型的“文件 / 视图 / 帮助”顶部菜单和工作区顶部按钮在当前 Web Chrome 中没有对应 UI。原 V2.1 曾将这些区域列为有意排除项，但 `PRISM_SHELL_REVISION_2026-09-15.md` 已记录用户新的明确决定：按原型恢复菜单、模块 Tab 和自绘标题栏。因此不能再以旧规范的排除条款作为完成依据。

本轮菜单改造必须保持 `ui/navigation_model.py` 为功能、权限和导航动作的唯一来源。推荐先做展示层还原：从现有 `navModel` 派生分组和叶子弹层，保留所有真实叶子导航索引、选中状态、子菜单展开偏好、语言过滤和锁定权限；不把原型的设计展板、模拟通知、模拟导出和示例快捷键加入业务导航。

## 原型侧栏契约

原型 `model.js` 定义的侧栏分组顺序如下。每组按钮是展示层入口，点击后以 `popover(title, items, anchor)` 打开叶子菜单；它不是新增导航节点。

| 顺序 | 原型分组 | 组图标 | 叶子入口（原型名） | 生产导航对应 | 备注 |
| ---: | --- | --- | --- | --- | --- |
| 1 | 数据中心 | `database` | Oracle、MySQL、OceanBase、达梦、Redis、MongoDB | 18–23，属于现有数据中心父项 14 | 保留所有六个真实数据库入口 |
| 2 | 模型 | `spark` | 聊天、工作 | 16、17，现有模型父项 15 | 父项只负责展示分组，不新建 AI 页面 |
| 3 | 交付管理 | `rocket` | 需求管理、发版联动、接口文档更新、日报 | 10、2、3、9 | 原型名称与生产组名一致 |
| 4 | 运维工作台 | `terminal` | 日志排查、命令库 | 13、6 | 组图标与生产叶子图标是两个层级 |
| 5 | 开发工具 | `code` | 加解密、接口排查、格式工具、证件类型、车辆 VIN | 5、12、11、1、4 | 保留顺序和叶子权限 |
| 6 | 个人效率 | `book` | 自我学习 | 8 | `private_unlocked` 为假时仍按现有权限过滤 |
| 7 | 设计展板 | `grid` | 图标与品牌、组件与提示、窗口与悬浮框 | 无真实生产导航索引 | 只属于设计参考，明确排除在业务侧栏之外 |

首页是独立入口，使用 `home` 图标；设置和悬浮工具栏在侧栏底部，是独立动作，不属于以上业务分组。原型在组按钮之间插入两条分隔线，位置在“模型”之后和“运维工作台”之后；首页之后还有一条分隔线。

原型的 `M(S.page).group === groupName` 会让当前页面所属组按钮显示紫色激活态。点击叶子才执行真实导航；点击组按钮本身不切换面板，只打开弹层。弹层首项获得焦点，点击外部或再次打开其他弹层会关闭当前弹层，弹层位置相对组按钮计算，并在视口上下左右留出约 10–12px 边距。

## 生产导航模型与展示映射

### 唯一权威不变

`ui/navigation_model.py` 中的 `NAV_MODEL`、`NAV_ITEMS`、`FIXED_DB_PAGES` 和 `build_web_nav_model_data()` 已经包含实现这套展示所需的业务数据：

- 14 是数据中心父级，子项由六个固定数据库入口组成。
- 15 是模型父级，子项是聊天 16 与工作 17。
- 10、2、3、9、13、6、5、12、11、1、4、8 是真实叶子入口。
- 7 是设置，单独放在侧栏底部。
- `private_unlocked=False` 时不返回自我学习 8，这是现有权限行为，不能由前端自行补回。
- 每个业务叶子仍以其原有导航索引调用 `bridge.navigate(index)`，不得改用原型的字符串页名作为新协议。

### 展示层需要做的派生

当前 DTO 的最外层 `groups` 以产品功能分组表达：`workspace` 内同时放首页和数据中心，`ai` 内放模型；原型则把首页单独置顶，并把数据中心、模型作为侧栏组按钮。因此实现原型外观时需要做一次纯展示派生：

1. 从 `workspace.items` 中把首页 0 单独渲染到组列表前。
2. 从带 `children` 的数据中心父项 14 派生“数据中心”弹层组，保留 18–23 子项。
3. 从带 `children` 的模型父项 15 派生“模型”弹层组，保留 16、17 子项。
4. `delivery`、`ops`、`devtools`、`personal` 直接以现有叶子项组成弹层组。
5. `settings` 始终由 `model.settings` 渲染到侧栏底部。

这一步只改变 DOM / QWidget 的展示组织，不创建新的 `nav_index`，不改变 `_show_panel` 或 Bridge DTO。若为了让原型组名、英文副标题和图标完全一致而需要补充展示字段，应由 Python DTO 一次性返回或由已有字段稳定派生，不能在 Vue 里复制一份业务导航表。

### 推荐的最小安全语义

采用两层展示规则可同时满足用户的“按原型”诉求和现有业务稳定性：

- 在宽屏展开模式，保留现有父分组的展开 / 折叠语义和用户偏好，避免改变用户已经依赖的数据库、模型子项显示状态；外观上把父项和叶子行调整成晴空棱镜的间距、颜色、激活态和动画。
- 在收起 / 紧凑模式，组按钮改为打开原型式玻璃弹层，弹层从同一份 `navModel` 取叶子项；这样所有叶子在窄侧栏仍可访问，且不要求把六个数据库按钮挤在 72–84px 的轨道内。
- 若用户最终坚持“宽屏也必须完全按原型”，可以把宽屏组按钮同样改为弹层，但要保留原父索引的展开偏好作为下次切回展开模式的状态，不删除配置键，也不改变子项导航。
- 组弹层关闭只关闭展示层，不销毁面板、不取消任务、不断开 SQL / SSH 会话。

该方案的关键是“父分组展开状态仍代表用户偏好，弹层只代表当前展示方式”。它避免把弹层误认为一个新页面，也避免以静态原型数组覆盖生产权限。

### 图标映射

Vue 使用本地 `IconSprite.vue` 和 `icons.ts` 的 `ROLE_TO_SYMBOL`，已覆盖当前导航模型使用的已知角色。没有必要引入图标 CDN 或新增第三方图标库。

| 原型层级 | 原型 role | 当前生产 role / symbol | 现状 | 处理建议 |
| --- | --- | --- | --- | --- |
| 首页 | `home` | `home → i-home` | 一致 | 保持 |
| 数据中心组 | `database` | 14 `database → i-db` | 一致 | 保持 20px 组图标 |
| 模型组 | `spark` | 15 当前 `chat → i-chat` | 可见差异 | 展示层将 15 的组图标派生为 `spark`；叶子 16 仍用 `chat`，17 用 `spark` |

| 运维组 | `terminal` | 生产叶子 `search → i-search`、`operations → i-term` | 组与叶子层级不同 | 展示层使用 `terminal`，叶子保持原有图标 |

原型组图标是 20px 左右，叶子弹层图标是 16px；Vue 当前父项约 20px、子项约 16px，原生父项约 20px、子项约 16px，尺寸可以复用现有值。改造重点是组 role 的展示映射，而不是替换 SVG 资源。

### 当前激活态差异

原型在当前页面所属组按钮上显示紫色背景和白色图标；弹层中的叶子没有独立的“当前页”强激活实现，主要靠弹层项 hover。当前生产实现则：

- Vue 只给当前叶子 `.active`，父项仅在 `openParents` 为真时使用 `sidebar-highlight`，并没有“当前页属于本组”的组激活态。
- 原生 `_show_panel()` 对 14、15 父索引跳过 checked，只有当前真实叶子按钮被选中；这保留了导航逻辑，但与原型组按钮激活态不同。

建议新增一个纯计算的 `activeGroup`：从当前 nav index 向下匹配叶子和其父项，组按钮使用 Prism 激活背景；弹层中的当前叶子可显示轻量选中标记，但仍以叶子 `i` 调用真实导航。不能通过新增页面或伪造选中索引实现。

### 提示和无障碍差异

原型组按钮有 `aria-haspopup="menu"`、`aria-label` 和 `title`；弹层有 `role="menu"`、`role="menuitem"`，打开后首项聚焦，边缘位置自动约束。当前差异：

- `ChromeApp.vue` 的父项和叶子有 `title`，但 `frontend/src/chrome/nav.ts` 在把 `children` 转成 `NavChild` 时没有保留 Python 子项的 `tip` 字段，子项 tooltip 实际回退为中文名称。
- 原生收起状态 `_nav_tooltip()` 使用 `display_name(index, language)`，提示短而统一，没有使用 `display_tooltip` 的详细说明。
- 当前原生 `nav-sub-expand` 有独立展开 tooltip，但它不是原型的组菜单入口；改造时需要区分“展开偏好提示”和“打开分组菜单提示”。

建议：保留 `tip` 作为可选字段并在 Web 校验器中透传；没有 tip 时回退为当前 `zh` / `en` 名称。为组按钮提供“打开〈分组〉菜单”的可访问名称，为弹层叶子提供原有业务 tip；键盘支持 Enter / Space 打开组，方向键或 Tab 移动，Esc 关闭并把焦点还给组按钮。原生 QMenu / 自绘弹层也应使用相同文本，不能在前端另写一套描述。

## 当前顶部菜单和按钮的缺口登记

### 需要主代理接线的文件

这些文件不能由本菜单子任务单独改动，需由主代理统筹：

- `main_window.py`：将菜单项映射到现有导航 / 快速面板 / 用户菜单动作，接入原生 fallback 侧栏的组弹层或 QMenu；保持 `_show_panel` 和面板缓存生命周期。
- `ui/page_chrome.py`：若顶部全局按钮由 ContextHeader 扩展，需在统一壳层方案中接线；本报告不单独修改。
- 自绘标题栏相关文件：由已批准的标题栏代理负责，不在此重复实现窗口关闭、最小化、最大化和置顶。
- 模块 Tab 相关文件：由 Tab 代理负责；菜单可以调用现有导航动作，但不拥有 Tab 生命周期。

### 不可修改的范围

- 不改 `ui/navigation_model.py` 的真实导航索引、权限和业务动作，除非主代理另行提出仅增加展示 DTO 字段的协调变更。
- 不加入原型设计展板为业务入口。
- 不增加 `completeTask`、`saveTask` 等无现有 Bridge 实现的接口。
- 不以静态原型模块数组覆盖动态 `navModel`。
- 不改启动、单实例、WebEngine 安全策略、用户数据路径、SSH 会话所有权和真实配置。
- 不操作用户运行包 PID 38548，不修改用户 `data` 或凭据。

## 建议的实现顺序

1. 先在 Vue 消费端写一个纯展示派生函数：输入现有 `NavModel`，输出首页、六个生产业务分组、设置；组内只引用现有 `NavItem` / `NavChild` 对象和索引。
2. 在宽屏保留现有父分组展开状态；在紧凑 / 收起状态将组按钮接到 `NavGroupMenu`，弹层以同一组叶子数据渲染。
3. 复用 `iconId()` 和 `IconSprite`，补齐组级 `spark / rocket / terminal / code / book` 展示映射；不要复制叶子图标映射。
4. 加入 `activeGroup` 计算和组级 `aria-current` / selected 视觉；当前叶子继续由 `current` 索引决定。
5. 保留已有父项 Enter / Space 行为；收起模式组按钮用 Enter / Space 打开弹层，Esc、外部点击和切换到另一个组关闭弹层。
6. 通过现有 Bridge 或主代理提供的最小动作适配器接入“折叠导航、快速面板、日报、关于、使用说明”等真实动作，逐项剔除原型模拟动作。
7. 生成嵌入 Web 资源后，再由主代理把同一展示语义接到原生 fallback；原生可使用 QMenu，但菜单数据仍来自 `NAV_MODEL` / Web DTO，不能再维护第二份叶子清单。

### 验收时要分开的证据

- 源码静态对照只能证明结构、索引和动作映射存在，不能证明窗口实际尺寸、WebEngine 命中和原生 fallback 视觉一致。

- 运行中的 Web 与原生窗口必须分别验证，尤其是紧凑模式、弹层边界、DPI、中文长文本和用户偏好恢复。

## 给主代理的停点与核准建议

本次只读审计已确认：菜单缺口是壳层展示缺失，不需要改业务功能；现有导航和叶子权限足以支撑原型分组。建议主代理核准下面的最小实施边界后，再开始生产改动：

- 组菜单数据只从 `navModel` 派生，保留全部真实叶子索引。
- 首页、设置、悬浮工具栏保持原型的独立位置。
- 宽屏保留现有父分组展开偏好，收起 / 紧凑模式使用原型玻璃弹层；如果用户要求宽屏也弹层，再在同一数据适配器上切换展示策略。
- 补齐组激活态、组级图标和子项 tip 透传；保留当前叶子导航动作。
- 设计展板、模拟通知、模拟导出和没有真实内容的快捷键不进入生产菜单。
- 菜单代理只修改列出的 Vue / 图标 / 样式 / 生成资源文件；`main_window.py` 顶部菜单和原生接线由主代理统筹，避免与标题栏、Tab 代理发生冲突。

在主代理核准前，本子任务不修改生产代码、不提交、不推送；新建的专属交接报告就是本次菜单审计的唯一输出。
