内网 Agent 工作台改造需求文档

把「模型对话」从纯聊天升级为类 Codex / WorkBuddy 的内网编程 Agent，内置 Superpowers 工作流，覆盖前后端开发 / 文档整理 / 需求 / 设计，全程不连互联网。

面向 Grok 开发 边界卡死 · 禁止扩大改动 无互联网 · 全内网 v1.0 2026-08-27

一需求总览与目标

当前「模型对话」面板（panels/model_chat_panel.py + tools/model_chat_store.py）已是一个能用的多轮聊天：支持新建/搜索/重命名/删除会话、复制、停止、重新生成、历史落盘 data/。但它有三个根本局限，本需求要逐一解决：

局限现状目标
① 纯聊天，无动手能力模型只能「说」，不能读写文件、改代码、跑命令类 Codex：绑定工作文件夹 → 读文件 → 改代码 → 写回 → 展示 diff
② 无 skill 机制 UI底层有 ptools_harness.TASKS 硬编码 3 任务，用户够不到内置 Superpowers + 内网 skill，用户可安装/启用/禁用
③ 会话不分类型只有一种「对话」，无「工作区/任务」概念区分「工作台（Agent 任务）」与「对话（闲聊问答）」两种形式
总基调沿用本软件一贯原则：不连互联网、数据落 config.local_data_dir()（升级不丢）、安全门禁（写命令/危险操作默认确认）、复用现有页面骨架四层规范，不另起一套风格。

二内置 Superpowers 工作流（skill 化）

Superpowers 是 MIT 协议的开源「编码 Agent 工作流 skill 集」，由 15 个可组合 skill 组成。它不依赖互联网、纯 Markdown 指令，可直接内网内置。我们把它翻译/适配为软件内的 skill 文件，挂在现有 skill 加载机制下。

3.2 注册机制：从硬编码到清单驱动

现有 ptools_harness.TASKS 是硬编码 dict，新增 skill 必须改代码。改为清单驱动：

# 新清单文件：data/harness/skills.json（用户可编辑）+ resources/ai_skills/manifest.json（内置默认）
{
  "tasks": [
    {"task": "sql.draft",      "skill": "sql.md",          "category": "后端开发", "builtin": true},
    {"task": "code.review",    "skill": "code_review.md",  "category": "后端开发", "builtin": true},
    {"task": "doc.summary",    "skill": "doc_summary.md",  "category": "文档整理", "builtin": true}
  ]
}
安全边界清单只负责「任务名 ↔ skill 文件」的注册映射，不放开任何执行权限。skill 只是给模型的提示词文本，模型仍受 sql_guard/linux_guard/ai_sql_draft 三道门禁约束。新增 skill 不能绕过写命令确认。

四模型对话改造：类 Codex 的内网 Agent

这是本需求的核心。把「模型对话」从纯聊天升级为能「绑定工作文件夹 → 读文件 → 改代码 → 写回」的 Agent。

4.1 现状与缺口

能力现状缺口
模型调用intranet_llm.chat_completions 同步 + SSE 流式，OpenAI 兼容无 function calling / tool use——这是 Agent 的核心
文件读写需求模块有 svn_workspace.py（SVN 文件树/增删改/commit/lock）无「任意本地目录」的通用文件读写封装
会话存储model_chat_store.py 完整（多轮、落盘、裁剪、标题）无「项目上下文 / 文件快照 / 工具调用记录」字段
skillptools_harness 硬编码 3 任务无清单驱动 + 无 UI

4.2 核心设计：受控工具调用（Tool Use）

内网模型多为 OpenAI 兼容接口，但不一定支持原生 function calling。为避免依赖模型能力，采用 「结构化输出 + 本地解析」的受控工具协议：

  1. 模型被告知可用工具清单（read_file / write_file / list_dir / search / run_test / run_svn 等），每个工具有 JSON schema 描述。
  2. 模型输出的回复里，若想调用工具，输出一个约定格式（如 <tool>{...json...}</tool> 或纯 JSON 代码块）。
  3. 本地 tools/agent_runtime.py（新建）解析模型输出 → 提取工具调用 → 本地执行工具 → 把结果回填给模型 → 循环，直到模型输出最终答案。
  4. 工具执行受 安全门禁约束：写文件/删文件/SVN 提交/danger 命令 → 弹「确认」；只读操作直接执行。
为什么用结构化输出而非原生 tool use① 内网模型不一定支持 function calling；② 本地解析可控、可审计、可脱敏；③ 与现有 ptools_harness 的 JSON 输出解析模式一致，复用已有 _extract_json_object。

4.2b 执行范式：ReAct + Plan & Execute 组合

工作台 Agent 采用 「先规划、后执行、执行中可再思考」的组合范式，兼顾可控性与灵活性：

  1. Plan（规划阶段）：接到任务后，模型先输出一份结构化执行计划（步骤清单 + 每步要调用的工具 / 要改的文件 / 预期结果）。由 Superpowers 的 writing-plans skill 提示词驱动。
  2. Execute（执行阶段）：按计划逐步执行，每步走 ReAct 循环——思考 → 输出工具调用（本地解析 JSON）→ 本地执行 → 观察结果 → 决定下一步，直到任务完成或触及轮次上限。
  3. 偏离即回规划：执行中若发现新情况、计划需调整（读到真实代码后需要改方案），允许回到 Plan 阶段重新出一版计划。
维度说明
范式ReAct（思考-行动循环）+ Plan & Execute（前置规划）组合
计划确认可跳过：默认出计划后自动进入执行；提供开关「始终先确认」供用户开启（开启后计划需人工确认/修改才执行）
写操作兜底无论是否开启「始终先确认」，写/删/覆盖操作仍强制 diff 预览 + 确认，计划确认开关不能绕过
循环上限单次用户请求最多 10 轮工具调用（含 Plan 阶段的计划产出轮），超出停止并提示
计划呈现计划以可折叠步骤卡展示在对话流中，每步执行完后打勾/标状态，用户可随时看到进度与偏差
Grok 必守① 计划确认开关默认「关」（自动执行），但必须留 UI 开关；② 写操作的 diff 确认门禁与「计划是否确认」是两套独立门禁，不可互相替代或省略；③ 计划与执行共用同一个 10 轮上限，不能让「出计划」无限消耗轮次。

4.3 受控工具清单（第一版，最小可用）

工具类型作用门禁
list_dir只读列目录（限定在会话工作文件夹内）无
read_file只读读文件内容（限会话工作文件夹内 + 大小上限）无
search_code只读在会话工作文件夹内按关键字/正则搜代码无
write_file写创建/覆盖文件确认 + diff 预览
edit_file写精准替换（old/new）确认 + diff 预览
delete_file危险删除文件二次确认 + 危险标红
run_test只读/半跑项目测试（pytest 定向）确认执行命令
run_svn危险SVN status/diff/commit（复用 svn_workspace）commit 二次确认
硬边界（Grok 必守）① 每个会话绑定一个工作文件夹（会话创建/导入时选定，可后续更换），文件操作默认落在该会话工作文件夹内；仍须用 realpath + commonpath 校验路径，拒绝越界读写 data/、resources/、系统目录、用户主目录、以及其他会话的工作文件夹；② 禁止执行任意 shell（不提供 run_shell 工具），命令只能通过白名单工具（run_test/run_svn）；③ 写操作必须展示 diff 预览 + 确认；④ 路径必须 resolve 到会话工作文件夹内的真实文件，禁止路径穿越。

4.5 工作文件夹（项目导入）

  1. 「工作台」新建会话时，绑定一个工作文件夹：选择本地目录（只读打开，不复制、不移动）。每个会话绑定一个文件夹做基础，后续的读取、生成、改写、删除等操作都发生在这个文件夹内。
  2. 导入后左侧显示该文件夹的文件树（复用现有文件树能力，或新建轻量 QTreeWidget 扫描）。
  3. 工作文件夹路径存 data/agent/workspaces.json，升级不丢。会话运行中可更换工作文件夹（更换后上下文里的旧路径快照随之刷新）。
  4. 导入时不扫描全量文件内容（避免卡顿），只记目录结构 + 常用文件类型白名单（.py/.js/.vue/.html/.css/.md/.json/.txt 等）。

七非目标（明确不做）

  • 不做联网模型、不做云端同步、不做插件市场在线下载。
  • 不做原生 function calling 依赖——一律走本地结构化输出解析。
  • 不做任意 shell 执行、不做多进程子代理并发（内网单机，改为顺序子任务）。
  • 不做 git worktree / 分支管理——内网用 SVN 或纯目录。
  • 不重写 intranet_llm/secure_store/db_connect/ptools_harness 的核心执行逻辑（只做 skill 清单化 + 工具运行时，不改三道安全门禁）。
  • 不做完整 IDE（不替代编辑器），只做「对话驱动的受控文件编辑」。
