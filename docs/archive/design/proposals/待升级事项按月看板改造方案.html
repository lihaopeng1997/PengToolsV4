待升级事项：按月选择、主动入选、独立完成态

基于当前实现核对后的最小改造方案 · 2026-08-10

确认后的目标行为

  1. 工作台“待升级事项”顶部增加上线月份下拉框；选中哪个月，只展示该月已勾选“是否本月上线”的需求。
  2. 删除工作台的“从需求添加”按钮和对应弹窗入口。
  3. 在“编辑需求”的上线月份字段下方增加“是否本月上线”复选框；它是需求进入待升级看板的唯一开关。
  4. 待升级看板每条任务后增加“已完成”按钮；点击后任务保留在当前选中月份，并显示“已完成”。

当前问题与根因

当前实现问题调整方向
仅按系统当前日期筛选，并强制要求 planned_online_date 属于当前月。无法查看指定月份；只有“上线月份”但没有计划日期的需求无法展示。改为按下拉框月份筛选 online_month，不再依赖计划上线日。
“从需求添加”通过看板隐藏 ID 的反向操作把需求放回。入口绕过了需求编辑台账，规则不直观。删除入口；只在编辑需求中以复选框控制是否入选。
没有完成态；需求状态与实际发版业务状态混在一起。若把按钮改成“已上线”会错误影响需求管理和发版流程。完成态只写入工作台看板配置，不修改需求的 status、实际日期或发版数据。

推荐实现方案

1. 编辑需求选择“上线月份”，勾选“是否本月上线”。保存到需求台账。
→
2. 工作台筛选月份下拉框选择 2026-08，仅取 online_month=2026-08 且复选框为真的需求。
→
3. 看板完成点击“已完成”，仅给该看板任务增加完成标识，任务仍显示。

数据边界

  • 需求台账新增字段：is_monthly_release（布尔值，旧数据默认 false）。
  • 看板独立配置新增字段：completed_requirement_keys，以“需求 ID + 上线月份”为键保存完成态；同一需求若改到另一个月，不会继承旧月份的完成状态。
  • 手工添加：保留现有“手工添加”；其完成态同样保存于看板配置，按手工事项 ID + 计划月份区分。
  • 兼容处理：旧 hidden_requirement_ids 继续读取但不再提供“从需求添加”恢复入口；本轮不删除历史配置，避免升级后报错。

看板展示规则

  • 月份下拉选项：当前月 + 所有“已勾选且填写上线月份”的需求月份 + 手工事项计划月份，按月份倒序排列。
  • 任务排序：未完成在前、已完成在后；同组内优先计划上线日，再按标题。
  • 未完成行：右侧按钮显示“已完成”。点击后即时刷新为绿色“已完成”状态。
  • 已完成行：显示完成标签；按钮改为“撤销完成”，便于误点恢复。
  • 点击需求行仍跳转需求管理；点击完成按钮不触发行跳转。

影响范围与验证

  • 涉及文件：panels/requirement_panel.py、panels/dashboard_panel.py、tools/dashboard_release_items.py，以及待升级事项定向测试。
  • 不改变：需求 status、actual_online_date、升级准备 SQL、发版 Excel、已有手工事项内容。
  • 回归覆盖：月份下拉筛选；未勾选不展示；不同月份不串项；完成/撤销完成只影响当前看板；旧看板配置兼容；“从需求添加”入口不存在。

实施确认

建议按以上方案实施。这样“是否进入哪个月的待升级事项”由需求编辑时明确决定，而“是否做完”只反映工作台执行进度，不会误改业务状态。
