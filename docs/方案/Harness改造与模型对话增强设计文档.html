一、背景与目标

软件已内置一套受控任务层 PTools Harness（tools/ptools_harness.py）与「基于 Schema 快照的字段证据链」TamengAgent（tools/tameng_agent.py），但模型对话入口（导航 15「模型对话」）目前是纯文本自由对话：模型不知道本地有真实的证件/VIN/信用代码生成逻辑，不知道已连接了哪些数据库、哪些 Linux 主机，回答时只能「按自己的知识猜」。

本次改造的核心思想只有一条：

把「模型自由生成」收口为「模型声明意图 + 本地受控执行」。
模型只负责理解用户意图、组织语言、声明要调用的工具；真正产生数据 / 查库 / 跑命令的，永远是软件内部已有的、经过校验的确定性逻辑。模型无权、也无法绕过这些逻辑自由编造。

本轮目标

  • 确定性数据（证件/VIN/信用代码）走软件生成逻辑
  • 数据库 / Linux 查询「先发现 → 再验证 → 后生成」
  • 对话思考过程 / 等待提示
  • Enter 发送、停止按钮、气泡内重新生成
  • 悬浮框大模型对话
  • 梳理 Harness 扩展方向与集成架构

非目标（明确不做）

  • 本阶段不实现，仅交付设计文档
  • 不引入公网模型 / 在线 CDN / 遥测
  • 不开放任意 shell（Linux 仍只读、白名单）
  • 不改变 SQL 控制台现有「绝不自动执行」红线
  • 不改账号/密钥/加密存储方案

2.2 三处「分叉 / 缺口」（本轮必须收口）

缺口 A — SQL 证据校验未打通到通用 Harness：
ptools_harness.sql.* 目前直接返回 strip fence 后的 SQL 字符串，没有走 tameng_agent 的字段证据校验。而 SQL 控制台走的是 ai_sql_draft + tameng_agent。两条链路校验深度不一致，模型对话入口是「裸奔」的。
缺口 B — Linux 规则两套口径分叉：
linux_guard 把 find / awk / sed / systemctl / journalctl 列为 denied，但 tools/ops_commands.py 命令库又把它们列为可用。同一命令在两处结论相反，必须统一收口到一套白名单。
缺口 C — 对话交互不完整：
默认快捷键是 Ctrl+Enter 发送、Enter 换行（与需求相反）；发送 / 停止是两个独立按钮；「重新生成」是全局底部按钮而非气泡内；无流式增量显示；_stop() 只置 cancelled 忽略结果，无法真正中断同步阻塞的 urllib 请求。

三、诉求一：确定性数据走软件逻辑

3.1 设计原则

身份证 / 护照 / 军官证 / 武警证件 / VIN / 统一社会信用代码，都是带校验位的强规则数据。模型自己编出来的数，校验位大概率是错的（身份证 MOD 11-2、VIN 第 9 位、信用代码 GB 32100 加权校验）。因此：

模型只能「声明调用工具 + 给出参数」，数据由本地函数生成后回填进回答。模型绝不直接输出这些字符串。

3.2 受控 Harness 工具契约（新增）

把这 3 组纯函数包装成 Harness 的本地工具（local tools），定义统一契约：

# 工具契约（JSON Schema 草案，实施时按此落地）

3.3 执行流程

用户：帮我生成 10 个湖南男性身份证 → 模型识别意图 → 声明工具 + 参数 → 本地函数生成 → 结果回填回答
  • 模型在 System Prompt 中被明确告知：这 3 类数据只能通过工具生成，如无法确定参数则追问，不得自造。
  • 工具返回结构化结果（数组），模型拿到真实数据后再组织成自然语言表格呈现给用户。
  • 校验兜底：即使模型「嘴硬」直接输出了一串数字，对话层可用 validate_resident_id / validate_vin / validate_code 做一次后置校验，命中「校验不过」的疑似自造数据时，提示用户「已改用本地逻辑重新生成」。

3.4 参数对齐（对齐现有 UI 面板）

工具现有 UI 面板需对齐的参数
证件证件类型（nav 1）证件类型、地区、年龄区间、性别、数量
VINVIN（nav 4）WMI、年份、能源类型、车型类别、数量

工具参数尽量与面板字段一一对应，保证「面板里能生成的，对话里也能生成，且结果一致」。

四、诉求二：思考过程展示与等待提示

4.1 现状

当前 _ChatWorker.run() 调 chat_completions(stream=True)，但 _decode_body 把 SSE 全文一次性拼接后返回，UI 只能等整段结束后一次性渲染，中间无任何过程反馈。

4.2 两个层次的「过程可见」

层次含义实现建议优先级
等待提示 模型思考/生成期间的占位反馈 发送后立即在对话区插入一个「正在思考…」的气泡（带三点跳动动画 / 骨架屏），收到首 token 后替换为真实内容。复用现有 pending 占位机制即可。 P0
流式增量 逐 token 显示回答 把 intranet_llm.chat_completions 改为真流式：解析 SSE 逐条 yield，_ChatWorker 通过信号把增量 append 到当前气泡。这是「等待提示」的最优形态。 P1
思考过程 展示模型的推理链（CoT） 需模型支持。若内网模型返回 reasoning_content / thinking 字段，则在回答前折叠展示「思考过程」；若模型不支持，则退化为「正在思考…」占位。注意合规：思考链属于模型内部推理，展示与否遵循模型供应商约定，默认可折叠隐藏。 P2
边界：「思考过程」依赖模型能力，不是纯前端能造出来的。设计上做到能展示就展示、不支持就降级为等待动画，两套都不阻塞主流程。

五、诉求三：数据库 / Linux 的「取证式」精准回答

5.1 核心原则

先发现 → 再验证 → 后生成，无证据不回答。
模型在自然语言转 SQL / Linux 命令时，禁止按自己的知识猜。因为软件已经连了数据库、连了 Linux，必须针对真实连接里的真实对象回答。
一句话：表名可以不精准（靠注释/同义词匹配），字段名必须精准（只能来自数据库查询结果）。

5.2 车险示例走查（对应你的原话）

用户说：「查询车险 main 表中的创建日期字段」

1 发现：查连接的库有无 main 表 → 2 匹配：命中 PRPCMAIN（车险主表） → 3 取字段：查该表真实列 → 4 出 SQL：CREATED_DATE 精准落列 
-- 用户意图：车险 main 表的创建日期字段
-- 实际数据库：表名是 PRPCMAIN（非 main），列是 CREATED_DATE

-- 步骤① 发现（本地执行，模型不可跳过）：
--   SELECT table_name FROM user_tables WHERE table_name LIKE '%MAIN%';
--   命中 PRPCMAIN（结合注释「车险主表」确认）

-- 步骤② 取字段（本地执行）：
--   SELECT column_name, comments FROM all_col_comments
--   WHERE table_name='PRPCMAIN' AND (column_name LIKE '%CREATE%' OR comments LIKE '%创建%');
--   命中 CREATED_DATE（注释「创建日期」）

-- 步骤③ 生成 SQL（字段名来自真实快照，精准）：
SELECT CREATED_DATE FROM PRPCMAIN WHERE ROWNUM <= 10;   -- Oracle 方言

其中「main → PRPCMAIN」靠 tameng_agent.FIELD_SYNONYMS 与表注释匹配；「创建日期 → CREATED_DATE」靠 _rank_field 的「注释精确 / 同义词扩展」命中。字段名绝不来自模型记忆，而来自 schema_snapshot 的真实列。

5.3 取证式编排（需下沉为通用 Harness 契约）

目前这套证据链只在 SQL 控制台（ai_sql_draft + tameng_agent）里生效；模型对话入口的 ptools_harness.sql.* 没走（缺口 A）。设计要求：

步骤动作责任方
① 意图解析识别用户是「查库」还是「跑 Linux」，提取关键词（main / 创建日期）模型
② 发现对象用 schema_snapshot.search_fields / 表名模糊匹配，列出候选表本地逻辑
③ 候选澄清候选 >1 时，把候选表/字段列给用户确认（复用 NEEDS_SELECTION 状态）本地逻辑 + 模型组织语言
④ 证据构建取真实列名 + 注释 + 索引，注入模型上下文（build_evidence_context）本地逻辑
⑤ 生成模型基于证据生成 SQL / 命令模型（仅组织）
⑥ 校验validate_generated_sql / linux_guard.inspect_command 拦截未知字段 / 危险命令本地逻辑
⑦ 输出校验通过才展示；否则打回重来或 fail-closed 拒绝本地逻辑
P0 收口（缺口 A）：让 ptools_harness.sql.draft / sql.optimize 也接入 tameng_agent 的 validate_generated_sql，实现「两条链路同一把尺」。
P0 收口（缺口 B）：统一 Linux 白名单。以 linux_guard 为准收口 ops_commands，明确 find / awk / sed / systemctl 是「只读可用」还是「禁止」，消除两套口径。

5.4 Linux 的「针对性」

与 SQL 同理：模型必须基于「已连接的 Linux 主机 + 白名单命令」回答，而不是泛泛给出命令。

  • 模型先确认当前连接的主机 / 项目上下文（复用 harness_project.project_context 的 log_hints、路径约定）。
  • 命令必须过 linux_guard.inspect_command，命中 denied（rm / reboot / sudo / 重定向）直接拒绝。
  • 查询需用户点「执行查询」才发 SSH（保持现有红线，绝不自动执行）。

八、诉求六：Harness 还能做什么

在「确定性数据 + 取证式查库 + 只读 Linux」之外，Harness 可进一步扩展为软件的统一受控工具总线。按「价值 × 落地成本」排序：

方向说明复用现有优先级
① 需求 → 升级准备 → 发版 Excel自然语言描述需求 → Harness 驱动模型生成 SQL 草案 → 走发版 Excel 模板release_prep.py、sql_panelP1
② 日报 / 学习库问答「我今天做了什么」→ 从需求/日报数据生成草稿（不覆盖已写内容）daily_reports.py、personal_knowledge.pyP1
③ 日志排查助手自然语言描述现象 → Harness 转成日志检索命令/关键字 → 引导导出ops_ssh.py、ops_log_panelP1
④ 接口排查解读抓到的报文（内存态）→ 模型解读字段/加密链路（严守不落盘）interface_debugP2
⑤ 格式 / 加解密辅助网关解密、格式工具的参数解释、VIN/证件校验说明各工具函数P2
⑥ 多系统 SQL 归一同一需求在 Oracle/MySQL/Dameng 多系统生成对应方言 SQLtameng_agent 方言层P2
统一范式：所有扩展都遵循同一模式 —— 「模型提意图 → Harness 路由到本地受控逻辑 → 本地执行/校验 → 结果回填」。Harness 的价值不是让模型「更会说话」，而是给模型接入软件已有的、可信的本地能力。

九、开发与集成 Harness：架构与分期

9.1 目标架构

对话层（model_chat / 悬浮框） → Harness 编排层（ptools_harness） → 受控工具（本地工具 + 证据链） → 本地逻辑（确定性生成 / schema / linux_guard）
  • 对话层：只负责渲染消息、捕获输入、展示工具调用结果；不直接碰数据库/命令/数据生成。
  • Harness 编排层：解析模型声明的工具意图，路由到对应受控工具，串起「发现→验证→生成→回填」。
  • 受控工具层：本地工具（证件/VIN/信用代码）+ 证据链工具（schema_snapshot + tameng_agent）+ 只读门禁（sql_guard / linux_guard）。
  • 本地逻辑层：复用现有纯函数，不新增业务规则，只做工具化包装。

依赖方向保持一致：对话层 → Harness → 工具/逻辑，工具层保持不 import PyQt / 不 import intranet_llm（现有 test_module_has_no_qt_db_or_llm 已锁定此约束，需继续守住）。

9.2 分期实施建议

阶段内容验收点
P0 收口期 ① 打通 ptools_harness.sql.* 到 tameng_agent 字段校验（缺口 A）；
② 统一 Linux 白名单（缺口 B）；
③ 对话交互：Enter 发送 / Alt+Enter 换行、发送↔停止切换、气泡内重新生成。 		同一句话在两个入口产出的 SQL 字段一致且精准；危险命令一律拦截；快捷键与按钮状态符合预期
P1 增强期 ① 确定性数据本地工具（证件/VIN/信用代码）接入对话；
② 等待提示 + 流式增量输出；

十、验收标准与非目标

10.1 验收标准（可测）

  • 确定性数据：对话生成 100 条身份证/VIN/信用代码，validate_resident_id / validate_vin / validate_code 校验通过率 100%，无模型自造（后置兜底命中即回滚重生成）。
  • 字段精准：「查询车险 main 表创建日期」在两个入口（对话 / SQL 控制台）产出的 SQL 均使用真实列名 CREATED_DATE 与真实表 PRPCMAIN；字段名绝不来自模型记忆。
  • fail-closed：无连接 / 快照缺失 / 快照过期时，模型不产出 SQL，而是提示「先连接数据库 / 刷新快照」。
  • Linux 安全：rm / reboot / sudo / 重定向等一律拒绝，白名单两套口径一致。
  • 交互：Enter 发送、Alt+Enter 换行；思考期间发送按钮显示为「停止」并可真正中断；气泡内「重新生成」与「复制」并排，只重生成当前条。
  • 悬浮框：可独立对话、置顶、拖拽、记忆位置，与主面板会话共享。

10.2 非目标（重申）

  • 不改账号/密钥/加密存储方案；不引入公网模型、CDN、遥测。
  • 不开放任意 shell；Linux 仍只读 + 白名单 + 需人工点「执行」。
  • 不改变 SQL 控制台「草案绝不自动执行」红线。
  • 不重写确定性数据生成算法（只做工具化包装）。
