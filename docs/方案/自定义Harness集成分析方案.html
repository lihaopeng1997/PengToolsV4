PengToolsHub 自定义 Harness 集成分析方案

只读调研结论 · 基于 PengToolsHub V4.27 Private 当前源码 · 2026-08-27

结论：适合建设复用现有 PTools Harness默认草案 + 人工确认不新增公网与通用执行能力

1. 结论摘要

可以，并且很适合。你的软件已经不是“普通桌面工具 + 聊天框”的起点：当前已有内网 OpenAI 兼容模型客户端、项目上下文包、SQL Schema 证据链、SQL/SSH 本地 Guard、模型工作台和日志排查的人工执行确认机制。最合适的路线不是另起一套 Agent 平台，而是把现有 tools/ptools_harness.py 演进为统一的 PengTools Harness Runtime。

推荐定位：大模型只负责理解、归纳、规划和生成受约束草案；Harness 负责取数边界、上下文脱敏、工具白名单、结果校验、风险分级和人工确认。任何实际连接数据库、发送 SSH 命令、写文档、变更需求状态、重放接口请求，始终由现有工具层在用户明确操作后执行。

本次仅分析，未修改任何 Python、QSS、配置、测试、构建脚本或 Git 内容。

2. 已有基础：不是从零开始

已有能力当前落点价值
内网模型接入tools/intranet_llm.py默认关闭；仅允许本机/RFC1918/link-local；每次请求解析地址防 DNS 重绑定；绕过系统代理；Token 使用 DPAPI/enc。
通用任务入口tools/ptools_harness.py已登记 sql.draft、sql.optimize、linux.query 三类任务，并加载项目 Profile 与可覆盖的技能文本。
项目知识包tools/harness_project.py支持项目 Profile、表名摘要、日志提示与用户自定义技能；业务源码不会被打进 EXE。
SQL 证据闭环tools/tameng_agent.py、tools/ai_sql_draft.py、tools/schema_snapshot.py通过有效 Schema 快照、表/字段证据、方言和本地校验生成草案，且 SQL 控制台不会由模型直接执行。
SSH 只读门禁tools/linux_guard.py、panels/ops_log_panel.py模型生成命令后再次本地校验；用户点击确认才发送到当前 SSH 标签会话。
高敏会话边界panels/interface_debug_panel.py抓包请求/响应仅留内存；停止抓包保留会话，清空或退出才清理，符合不落盘原则。
现状判断：AiWorkbenchPanel 的 SQL 生成已经比通用 ptools_harness.py 更严格；前者走 Schema 证据与 TamengAgent，后者 SQL 分支仍偏“返回文本草案”。后续应收敛为一个统一的任务契约，而不是让两条 AI 路线继续平行演化。

3. 建议目标架构

页面按钮 / 模型对话「任务模式」 ↓（仅传最小、脱敏、可解释上下文） PengTools Harness Runtime ├─ Task Registry：任务名、输入 Schema、输出 Schema、提示词、能力级别 ├─ Context Builder：项目 Profile / Schema 证据 / 用户显式选区 / 长度上限 ├─ Policy Engine：敏感数据规则、风险等级、人工确认、禁止任务 ├─ Local Validators：SQL Guard、Linux Guard、字段范围、JSON/文档结构校验 ├─ Tool Adapters：仅调用既有 tools/ 的受控函数 └─ Result Presenter：解释、草案、风险、下一步；不隐式执行 ↓ 内网模型（仅负责结构化输出） → 本地复核 → 用户点击「应用 / 执行 / 导出」

架构决策

决策建议原因
代码组织新增 tools/harness/ 专用包，保留既有 tools/ 业务函数不大规模重构；将注册、策略、上下文、校验与适配器聚合，避免 UI 直接拼 Prompt。
模型协议强制 JSON 输出 + 本地 Schema 校验；失败即降级为“原始草案，不可执行”模型格式不稳定时仍 fail closed，避免解析失败后误进入执行链。
工具调用不让模型直接拥有 shell、文件系统、数据库连接或网络请求模型只能选择已注册任务；具体操作必须经本地适配器和 Guard。
审计只记录任务名、时间、状态、风险、耗时和内容摘要/哈希；不记录 Prompt、Token、SQL 行数据、抓包正文兼顾可排障性与现有敏感数据不落盘约束。
交互模型对话默认“只聊天”；用户主动切换到“受控任务模式”才展示工具能力避免聊天上下文无意调用业务工具，也让每次操作意图清晰。

4. 统一风险模型：先定边界，再扩功能

等级能力范围模型是否可触发执行规则
L0 本地确定性格式化、校验、生成校验码、解析 SQL/DOCX无需模型优先用已有纯函数；不能为了“AI 化”替换可靠规则。
L1 AI 建议摘要、说明、分类建议、排查思路、测试点建议可以只返回文本或结构化建议，绝不修改台账、文件或远端状态。
L2 AI 草案SQL、文档变更说明、命令参数、接口草稿可以必须展示差异/风险；用户点“应用”才写入编辑器，应用后仍不执行。
L3 受控只读查询数据库 SELECT、SSH 只读命令、日志检索只能生成候选本地 Guard 复核 + 连接/快照/会话有效 + 用户二次确认，才执行。
L4 变更与高敏数据库写入、服务重启、文件写入、接口重放、凭据/报文禁止直接触发模型最多提出步骤清单；不得执行、不得代填、不得持久化敏感内容。
绝对禁止：开放式 shell；全盘文件读取/删除；模型驱动的数据库 DML/DDL；自动 SSH 变更；模型直接读取网关明文、接口抓包正文、Cookie、Authorization、密码、Token、业务数据行；从普通聊天自动调用任何工具。

6. 当前不建议接入模型的区域

接口排查（默认不接入）抓包正文、请求头、Cookie、令牌和响应通常高敏，当前实现明确“仅内存”。即使是内网模型，也不应把原始报文放进 Prompt。未来若确有需求，只能新增“用户手工确认后的字段级脱敏摘要”模式，且单独评审。
网关解密密钥、明文和报文已有不落盘原则。禁止被模型读取、总结或用于任何训练/日志语料。
证件 / VIN / 统一社会信用代码生成这些是确定性算法能力，不需要模型；增加模型只会降低准确性，并可能扩大不必要的滥用面。
运维变更动作停止/重启服务、kill、chmod/chown、容器重启、Kubernetes rollout、远程文件改写均保持人工工具流。模型只能给“检查前提和回滚清单”。
接口请求重放模型可以在未来协助生成脱敏的 Postman/cURL 草稿说明，但不能代替用户点击发送，更不能自行选择环境或携带认证信息。
普通模型对话自动工具化ModelChatPanel 应保持纯聊天。只有用户显式选中“受控任务模式”、明确任务与数据范围后，才进入 Harness。

7. 当前需要先收口的四项问题

  1. 统一任务结果协议。将 ptools_harness.run_task() 的 SQL 文本结果与 ai_sql_draft.generate_sql_draft() 的结构化草案结果统一。每个任务都应返回 task_id / status / summary / draft / evidence / risk / warnings / next_action。
  2. 统一 Linux 规则来源。tools/linux_guard.py 的只读白名单与 tools/ops_commands.py 的运维命令库并不完全一致。应让注册表按“任务类别—命令模板—风险级别—参数校验”提供唯一事实来源，避免模型允许而执行层拒绝，或反向出现漏网命令。
  3. SQL 所有入口走同一 fail-closed 校验。SQL 控制台已具有证据链；升级准备页的 sql.draft/sql.optimize 也应获得结构化警告、单语句校验、语句类别标识和“仅草案”状态，不应只依赖文本展示。
  4. 上下文最小化与提示注入隔离。数据库注释、文件名、日志和需求附件都必须视为不可信数据，以明确分隔块传递；任何来自数据里的“忽略指令”“执行命令”等文字不可改变系统策略。
历史复核事项：仓库内已有 AI_SQL控制台开发检查报告.html 记录过 Token 与快照绑定、同名字段限定、过期快照准入、Redis 字段模型等高优先级审查项。扩展 Harness 前应按当前源码重新跑定向安全回归，确认这些边界已闭合；不要仅以旧报告或界面展示作为通过证据。

8. 分阶段实施建议

阶段交付范围不做什么验收重点
P0：Runtime 收口任务注册表、统一 JSON 契约、Policy Engine、上下文脱敏器、统一审计元数据；将现有 3 个 PTools 任务迁入。不新增页面、不增加模型权限、不改变已有执行方式。无注册任务不能调用；模型格式异常不可执行；敏感字段在 Prompt/审计中不可见；所有现有定向测试通过。
P1：SQL + 日志SQL 统一草案契约；日志从“自由命令生成”升级为“命令库检索 + 参数填充 + 只读确认”；日志摘要仅选区输入。不支持跨库、写 SQL、SSH 变更、远端落临时文件。恶意 Prompt、错误表字段、SQL 多语句、危险 shell、过期快照、空 SSH 会话均必须被拦截。
P2：需求 + DOCX + 日报需求分析/测试点/上线清单建议；DDL 到文档更新计划；日报和风险摘要草稿。不自动写 JSON、DOCX 或改状态；不让模型读取完整附件。用户必须逐条采纳；生成结果可回退；DOCX 仍按现有预览/确认流程写副本。
P3：低风险解释能力格式错误解释、模型对话“任务模式”、项目技能包管理 UI。不开放任意 Python/shell/文件工具；不把接口排查原始报文纳入能力。任务范围可见、数据范围可见、模型不可越权、离线打包不引入公网依赖。

9. 每类任务的标准契约（建议）

请求： { "task": "ops.log_query_plan", "input": {"intent": "定位订单号超时", "selected_log_excerpt": "…"}, "context_ref": {"server_id": "仅本地引用", "service_id": "仅本地引用"}, "user_confirmed_scope": ["selected_log_excerpt"] } 模型可见上下文：只包含任务说明、脱敏后的显式输入、允许的候选命令模板/Schema 证据。 响应： { "status": "draft", "summary": "…", "draft": {"command_id": "logs.grep_context", "params": {"keyword": "…"}}, "evidence": ["用户选定日志片段"], "risk": "read_only", "warnings": [], "next_action": "请确认后填入终端命令栏" } 本地后处理：任务 Schema 校验 → Policy 校验 → 本地 Guard → 用户确认 → 既有工具函数执行

10. 测试与发布门槛

  • 每一个 Task 有纯函数级输入/输出验证、恶意模型输出、空值、超长文本、错误 JSON、提示注入文本和脱敏测试。
  • SQL：快照过期、跨连接 Token、未确认字段、同名字段、JOIN 假设、多语句、CTE 包裹 DML、方言错误均 fail closed。
  • Linux：模型返回 rm、重定向、解释器管道、未注册命令、参数换行、链式命令均拒绝；命令库模板仅可使用经允许的参数。
  • 文档/需求：模型建议不能自动落库；只有用户点采纳后调用既有保存/更新函数。
  • 隐私：对模型请求体与审计元数据写单测，确保不存在密码、Token、Authorization、Cookie、完整连接串、业务行数据和抓包正文。
  • 每轮可验收改动仍执行定向测试、scripts/scan_release_secrets.py、scripts/build_release.ps1，并核对 dist/PengToolsHub.exe、Installer/PengToolsHub.exe、PengToolsHub_Offline_Setup.zip 与 resources/build_info.json。

11. 建议的首个可交付版本

建议先只做“P0 Runtime 收口 + P1 SQL/日志”，不急于把所有模块都接进来。这样能在不扩大敏感数据面、不改现有产品边界的前提下，最快让用户感受到价值：

  1. SQL：自然语言 → 有证据的查询草案 → 本地复核 → 人工执行。
  2. 日志：自然语言 → 已有命令库中的只读检索计划 → 本地 Guard → 当前 SSH 标签人工确认执行。
  3. 统一页面展示：任务名称、输入范围、模型可见数据摘要、风险、校验结论和“下一步由谁执行”。
预期效果：把模型从“可能会乱猜的聊天助手”变成“只在明确业务边界内协助产出草案的受控专家”，并保留 PengToolsHub 现有离线、私网、凭据保护、敏感内容不落盘与人工审批的核心价值。

12. 后续待确认事项

  1. 日志片段是否允许发送给已配置的内网模型？建议默认关闭，用户每次显式勾选“仅发送本次选中且已脱敏片段”。
  2. 需求附件是否允许做“用户选择文本段落”级别分析？建议先仅支持标题、描述和已人工粘贴的片段。
  3. 是否将“SQL 优化”限定为只读查询优化？建议是；DML/DDL 仅返回审阅建议，不产生可执行改写。
  4. 是否需要在设置中增加“任务权限总开关 / 各任务开关”？建议保留全局默认关闭，并提供 SQL、日志、需求、文档四类独立开关。
