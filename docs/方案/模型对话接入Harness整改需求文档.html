模型对话接入 Harness 整改需求文档

让「模型对话」入口在回答 SQL / Linux 类问题时，先走字段证据链与只读白名单，做到「表名可模糊、字段名必须精准」。

项目：PengToolsHub V4.27 Private 技术栈：Python 3.12 + PyQt6 交付对象：Grok（开发执行） 本文档定位：只出方案，不改代码

1现状与根因（一句话说清为什么「没接」）

Harness 能力已经在软件里，但只接在「数据中心（原 SQL 控制台）」入口，「模型对话」入口是裸奔的。

1.1 当前各入口接线情况

入口是否接 Harness代码证据
数据中心（SQL 控制台）✅ 已完整接入panels/ai_workbench_panel.py:30 引 prepare_request / validate_generated_sql / format_evidence_bar
升级准备 / 日志排查✅ 部分接入sql_panel.py:51、ops_log_panel.py:57 引 ptools_harness.run_task
模型对话❌ 未接入panels/model_chat_panel.py 全文 零引用 harness / tameng_agent

1.2 根因（代码级）

模型对话面板的核心链路只有一条「通用聊天」：

model_chat_panel.py
  _send()                      # 用户点发送
    → append_message(...)       # 追加 user 消息
    → _start_worker(payload)    # payload = SYSTEM_PROMPT + 历史消息
      → _ChatWorker.run()       # 后台线程
        → chat_completions(messages, cfg)   # 直接问模型，无任何证据
        → completed.emit(text)  # 回显

这条链路里 没有「当前连接」、没有「Schema 快照」、没有「字段证据」、没有「Linux 白名单」 的任何概念。所以用户问「查车险 main 表的创建日期」，模型只能凭自己猜，猜错表名/字段名它也不知道。

关键事实 「数据中心」面板已经有一条完整可复用的证据链，本方案就是把这套链路「搬到」模型对话入口，而不是新写一套： _browse_conn() 拿当前连接 → load_snapshot(conn_id) 拿快照 → prepare_request() 做 gate + 候选解析 → generate_sql_draft() 调模型 → validate_generated_sql() 校验 → 拦截或落盘。

2开发边界（5 条铁律，防止改错）

本轮改造只做一件事：给「模型对话」入口加一层「取数意图识别 + 证据链前置校验 + Linux 只读门禁」。除此之外一律不碰。

② 不改 tameng_agent.prepare_request / validate_generated_sql 的签名与语义——它们是数据中心的验收基线。
③ 模型对话的通用聊天能力必须保留：非取数意图的消息仍走原 _send → chat_completions 链路，不得拦截、不得降级。
④ 证据链里绝不注入：真实密码、Token、Cookie、完整连接串、任何业务行数据。只注入「表名、字段名、类型、注释、索引」等结构元数据。

3.1 SQL 类：证据链前置校验（复用数据中心逻辑）

核心原则：先发现 → 再验证 → 后生成。表名可模糊，字段名必须精准（因为字段来自真实扫描的快照）。

步骤 A：模型对话面板自带「连接选择器」拿到当前连接和快照（方案 B，已拍板）

为什么模型对话面板拿不到连接：连接列表是全局落盘的（data/harness/connections.json，任何面板调 load_connections() 都能读），但「当前选中了哪一条」只存在数据中心面板私有的 conn_combo 下拉框内存里（ai_workbench_panel.py:753 的 _current_conn()）。两个面板是平级兄弟，模型对话面板看不见数据中心的选中状态。

已拍板方案 B：模型对话面板自己放一个连接下拉框，数据源就是 load_connections()，用户在这个页面明确「针对哪个连接问」。不继承数据中心的选中项（避免隐式耦合），不碰 db_connect.py（只调用其 load_connections() 读取函数，不改写）。

from tools.db_connect import load_connections
from tools.schema_snapshot import load_snapshot

# ① 初始化：模型对话工具栏新增一个连接下拉框 self.conn_combo（只读展示，可切换）
#    填充方式复用数据中心的 _reload_connections 同款逻辑（ai_workbench_panel.py:772）：
rows = load_connections()                      # list[dict]，每条含 id/name/dialect/host 等
for item in rows:
    self.conn_combo.addItem(str(item.get('name') or item.get('id')), item)

# ② 发送时读当前选中项：
conn = self.conn_combo.currentData()           # dict | None
conn = dict(conn) if isinstance(conn, dict) else None

# ③ 拿快照：
snap = load_snapshot(str(conn['id'])) if conn else None   # dict | None

依赖函数（已存在，直接调用，禁止改动）：

  • load_connections() → 返回连接列表（db_connect.py:77）
  • load_snapshot(conn_id) → 返回该连接的结构快照（schema_snapshot.py:77）
连接下拉框的三条硬约束 ① 只读展示 + 可切换，不提供新增/编辑/删除（编辑连接仍走数据中心）。
② 无任何连接时，下拉框显示「未配置数据库连接」，取数意图直接提示去数据中心配置。
③ 下拉框项里 不得渲染密码字段（连接对象里的 password 是加密串，仅用于连接，绝不进提示词、绝不进 UI）。

步骤 B：调用 prepare_request 做门禁 + 候选解析

from tools.tameng_agent import prepare_request

prepared = prepare_request(question, snap, conn)
# 返回 dict，关键字段：
#   ok: bool          是否放行调模型
#   state: str        READY / NEEDS_SELECTION / BLOCKED / NO_CONNECTION / SNAPSHOT_MISSING / SNAPSHOT_STALE
#   reason: str       拦截/提示原因（可直接展示给用户）
#   next_action: str  下一步建议
#   evidence: dict    字段证据上下文（仅 ok=True 时有）
#   call_model: bool  是否允许调模型

prepare_request 内部会依次做（tameng_agent.py:633）：

  1. snapshot_gate(conn, snap)：无连接 / 无快照 / 快照过期 → 直接 BLOCK，不调模型。
  2. extract_intent_terms(question)：从问题里抽表名词、字段词、排序/索引/关联意图。
  3. resolve_candidates(snap, intent)：在快照里做表名模糊匹配（精确/归一化/注释）、字段名精准匹配；命中多个候选字段 → 返回 NEEDS_SELECTION。
  4. build_evidence_context(resolution, snap)：生成「已确认字段 + 表 + 索引」证据块。

步骤 C：按 state 分流处理

state含义模型对话面板应做的动作
READY + ok=True证据齐全，可生成进入 3.2 调模型
NEEDS_SELECTION多个候选字段把 resolution.fields 列出，让用户点选（气泡内渲染候选列表），选定后带 confirmed=... 重新调 prepare_request
BLOCKED无证据/需补关联把 reason 作为助手消息直接回显，不调模型
NO_CONNECTION 等缺连接/缺快照提示「请先在数据中心选择连接并扫描结构」

步骤 A-2：快照缺失/过期的兜底（已拍板，现场扫描 + 明确提示）

load_snapshot(conn_id)（schema_snapshot.py:77）读不到文件时直接返回 None——即用户从没在数据中心扫过该连接，模型对话里就没有它的字段证据。此时不允许调模型猜字段，也不允许静默失败。

已拍板的兜底策略（按顺序执行）：

  1. 若 snap is None：先回显一条助手消息「该连接尚未扫描结构，正在扫描…」，然后现场触发一次 scan_schema(conn)（schema_snapshot.py 的入口）拿到快照，成功后继续证据链。扫描必须在后台线程，避免阻塞 UI。
  2. 若现场扫描失败（连接不通/无权限）：回显「扫描失败：{原因}，请先到数据中心确认连接可用」，不调模型，结束。
  3. 若快照存在但过期（snapshot_gate 返回 SNAPSHOT_STALE）：提示「结构可能已变化，建议到数据中心重新扫描」，仍可按旧快照继续（不强制阻塞），把「可能过期」作为警告回显。

现场扫描的边界：只调 scan_schema 这一个既有函数，不改其内部实现；扫描是只读的结构读取，不执行任何业务 SQL。

3.4 Linux 类：只读门禁（复用 run_task 或直接 inspect_commands）

两种实现，推荐方案 B（更轻，不用改 harness）：

方案做法评价
A调 ptools_harness.run_task('linux.query', question, cfg=cfg)会走 skill 提示词 + inspect_commands，返回 {summary, commands, allowed, rejected, risk}；但依赖项目上下文加载，偏重
B（推荐）先让模型把自然语言转命令（或直接识别），再调 inspect_commands(commands) 过滤只复用 linux_guard.inspect_commands，白名单/黑名单逻辑复用，链路干净

方案 B 具体逻辑

from tools.linux_guard import inspect_commands

# 1. 调模型，system 提示词约束「只输出只读命令」
# 2. 拿到命令列表后过滤：
allowed, rejected = inspect_commands(command_list)
# allowed: list[str]   放行的只读命令
# rejected: list[(cmd, reason)]  被拦命令 + 原因

# 3. 回显给用户：
#    - allowed 的命令可展示
#    - rejected 的命令必须附「已拦截：原因」，绝不执行

inspect_commands（linux_guard.py:101）内部基于：ALLOWED_BINARIES（grep/tail/cat/ls/ps/df...）、_DENIED_BINARIES（rm/mv/kill/chmod/sudo/systemctl/find/awk/sed...）、_DENIED_PATTERN（重定向/管道到解释器/危险命令）。天然禁止破坏性命令。

注意（Linux 白名单口径分叉，必须选一套）：项目里存在两套 Linux 白名单——tools/linux_guard.py 的 ALLOWED_BINARIES，与 tools/ops_commands.py（运维助手用的）那一套。二者在 find / awk / sed / systemctl 等命令的放行口径上不一致。本接入已拍板统一采用 linux_guard.inspect_commands 这一套（因为它与数据中心/证据链同源、链路干净），不允许 Grok 再引入 ops_commands 那套来「对齐」，否则模型对话和运维助手的拦截行为会分叉、更难排查。口径差异留待后续单独统一，不在本轮范围内。

注意：Linux 查询的实际执行仍在「数据中心 / 运维助手」里由用户点「执行查询」才发 SSH。模型对话入口只生成并展示命令，绝不自动执行。

3.5 意图识别怎么判断「取数」还是「闲聊」

关键：不能误伤通用聊天。建议一个轻量规则，新建独立文件 tools/chat_intent.py（注意：这个文件当前不存在，是新增文件，不是修改已有文件）：

SQL_INTENT_KEYS = ('查', '查询', 'select', '表', '字段', '列', '数据库',
                   '创建日期', '创建时间', '统计', '合计', 'count', '索引', '关联', 'join')
LINUX_INTENT_KEYS = ('日志', '查日志', 'tail', 'grep', '看下进程', '磁盘', '内存',
                     'ps', 'df', 'free', '主机名', 'cpu')

def detect_take_data_intent(text: str) -> str:
    """返回 'sql' / 'linux' / 'none'"""
    t = text.lower()
    if any(k in t for k in LINUX_INTENT_KEYS): return 'linux'
    if any(k in t for k in SQL_INTENT_KEYS):   return 'sql'
    return 'none'

只有 detect_take_data_intent 返回非 none 时才走证据链；否则完全走原通用聊天链路，零影响。

4已拍板的 5 项决策（Grok 照做，不必再问）

#决策点最终结论落地位置
1模型对话如何知道「当前连接」？方案 B：模型对话面板自带连接下拉框（数据源 load_connections()，只读 + 可切换，不继承数据中心选中项，不碰 db_connect.py）3.1 步骤 A
2快照缺失/过期怎么兜底？缺失→后台现场 scan_schema 一次；扫描失败→提示去数据中心、不调模型；过期→警告但按旧快照继续3.1 步骤 A-2
3取数模式是默认开还是手动开关？默认开，但只对命中的 SQL/Linux 意图生效；通用聊天永远走原链路3.5
4Linux 白名单两套口径分叉用哪套？统一用 linux_guard.inspect_commands，禁止引入 ops_commands 那套「对齐」，分叉问题本轮不处理3.4
5NEEDS_SELECTION（多候选字段）怎么交互？气泡内渲染可点选候选字段 chips（简单 QPushButton 列表），点击后带 confirmed 重发3.1 步骤 C
结论：以上 5 项已由用户拍板，Grok 拿到即可照做，不得自行更改默认值、不得因拿不准而停滞。若实现中遇到文档未覆盖的细节，按「只读、不执行、不碰红线、不注入敏感信息」四条底线取最保守做法，并在交付说明里注明。

5验收标准（Grok 自测 + 你验收）

  1. 通用聊天不受影响：问「写一段周报」「翻译这段」等非取数问题，行为与改造前完全一致。
  2. 无连接时：问「查车险主表创建日期」，回复「请先在数据中心选择连接并扫描结构」，不调模型。
  3. 有连接 + 有快照：问「查 main 表的创建日期」，若快照里实际是 prpmain 表 + CREATE_DATE 字段，回复的 SQL 必须用 prpmain.CREATE_DATE，字段名精准。
  4. 模型瞎编字段：模型返回了快照里不存在的字段，必须被 validate_generated_sql 拦截，回显「草案引用了不存在的字段 X」。
  5. 多候选字段：命中多个「创建日期」时，气泡内出现候选列表让用户点选，选定后重新生成。
  6. Linux 只读：问「查下最近的错误日志」，命令若含 rm / kill / sudo / >，必须被 inspect_commands 拦截并标注原因。
  7. 敏感信息零注入：检查发往模型的 messages，不得出现密码/Token/完整连接串/行数据，只有结构元数据。
  8. 绝不自动执行：生成的 SQL 和 Linux 命令都只展示，不写入执行器、不自动发送。

6非目标（本轮明确不做）

  • 不改「数据中心」面板任何逻辑（它是已验收基线）。
  • 不做流式逐字渲染（现有 chat_completions 已是阻塞聚合返回，改造不改变这一点）。
  • 不做自动执行 SQL / Linux 命令。
  • 不做「证件 / VIN / 信用代码走软件逻辑」——那是第二轮设计文档的范围，本轮不混入。
  • 不改连接管理、凭据加密、依赖打包。
