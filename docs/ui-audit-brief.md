# PengToolsHub 企业级 UI 审阅与整改任务书

你是一名资深桌面应用 UI 工程师。请对 PengToolsHub 做一次**企业级标准**的 UI 全面审阅，**并直接整改**：查出的问题按本文的基准和级别当场改掉，目标是把这个工具打磨成企业级应用的界面水准。验收由用户本人运行应用完成，你负责把改动做干净、把账记清楚。

## 项目背景（先读，不要跳过）

- 技术形态：Windows 桌面应用，Python 3.12 + PyQt6 为主体，局部 Vue 3 前端（侧边栏/仪表盘等轻量全局呈现）。分层架构以仓库根目录 `AGENTS.md` 为准：run → main_window → panels → tools / ui / config。
- 审阅基准分支：`MuseBulid`。
- 本项目**已经有一套设计系统**，它们是全仓 UI 的唯一权威来源，审阅时一切以它们为标尺：
  - `ui/theme_manager.py`——语义主题令牌（颜色/主题的权威）
  - `ui/layout_metrics.py`——布局与响应式模式（间距/尺寸的权威）
  - `ui/design_system.py`、`ui/field_metrics.py`、`ui/dialog_buttons.py`、`ui/page_chrome.py`、`ui/navigation_model.py`、`ui/selection_delegate.py`、`ui/icons.py`、`ui/motion.py`、`ui/responsive.py`
- 已知现状数据（供你验证和深挖，不许直接抄进结论）：全仓 `setStyleSheet` 约 966 处、`setFixedHeight` 约 859 处、`setFixedSize` 约 403 处、`setContentsMargins` 约 758 处、`QComboBox` 相关约 754 处、`customContextMenuRequested` 约 18 处。设计系统存在、但各 panel 大量硬编码绕开它——这正是本次审阅的核心命题。
- 体量提醒：`main_window.py` 约 97KB；panels 共 21 个文件，其中 `interface_debug_panel.py` 约 219KB、`requirement_panel.py` 约 206KB、`ops_log_panel.py` 约 198KB、`sql_console_panel.py` 约 106KB。文件大不是借口，必须逐个审完。

## 审阅范围（全量，不许抽查）

1. `main_window.py`（导航、主框架、面板容器）
2. `panels/` 全部 21 个文件，逐个过
3. `ui/` 全部公共组件，逐个过
4. Vue 前端：`frontend/` 源码与 `resources/webui/` 的关键呈现（与 PyQt 侧的一致性）

报告开头必须附**已审文件清单**，与上述范围逐一对账，缺一个要在报告里说明原因。

## 审阅维度（逐项排查，每项必须给结论；没问题也要写"已查，无问题"）

1. **布局与间距**：`setContentsMargins`/`setSpacing` 取值是否收敛到 `layout_metrics` 的刻度（或 4/8pt 网格）；同级元素间距是否一致；标签与输入框的对齐基线；分组留白；窗口缩放、最小尺寸、低分辨率（1366×768）下的挤压、溢出、文本截断；Splitter 的默认比例与拖动行为。
2. **控件尺寸**：按钮是否分级统一（主按钮/次按钮/危险按钮/图标按钮的高度与内边距）；输入框高度与同排按钮是否对齐；`setFixedHeight`/`setFixedSize` 的每处硬编码——该固定的固定、该弹性的是否被写死；表格行高、列表项高度、点击热区是否达标。
3. **样式与主题**：颜色是否全部走 `theme_manager` 语义令牌；逐一列出硬编码 hex/rgb 的位置；966 处 `setStyleSheet` 中哪些是重复造轮子、哪些与令牌冲突；圆角、边框、阴影是否一致；明暗主题下是否有漏网元素。
4. **字体统一（专项，用户特别强调）**：已知设计系统**没有字体令牌**——`theme_manager.py` 只有一个全局 `font-size` 覆盖口子，`design_system.py` 无任何字体定义，所以字体不统一首先是设计系统缺位。按三步处理：① 先全仓盘点实际在用的字体——QSS 中的 `font-family`/`font-size`/`font-weight`、`setFont`/`QFont`、Vue 侧的 font 栈——列出实际出现的字体族清单、字号种类数并计数；② 在 `theme_manager.py`/`design_system.py` 补一套字体令牌：UI 字体族、等宽字体族（SQL/代码/终端用）、字号阶梯（如页面标题/分组标题/正文/辅助/小字的固定档位）、各档字重与行高，命名与现有令牌风格一致；③ 全仓收敛：各 panel 与 Vue 前端一律改用令牌，清除散写的字体定义，同一语义层级不许出现两种字号/字重。盘点结果与收敛结果都写进报告《设计系统执行情况》一节。
5. **交互状态完备性**：每个可交互控件的 hover / pressed / focus / disabled / selected 五态是否齐全且全仓一致；焦点框是否可见；Tab 键顺序是否合理；回车/Esc 的默认行为；快捷键是否有提示。
6. **下拉框（QComboBox / QMenu）**：下拉面板宽度与最长选项是否匹配、超长文本的截断与 tooltip；下拉箭头样式；展开位置是否会溢出屏幕；选项行高与间距；空选项/占位文案；可编辑与不可编辑下拉的行为差异是否合理。
7. **右键菜单与选中态**：18 处 `customContextMenuRequested` 是否统一走公共实现还是各写各的；菜单项的齐全性、排序、分组分隔线、快捷键右对齐、危险项（如删除）的视觉区分；**选中行/选中项的高亮是否全仓一致**（对照 `ui/selection_delegate.py`）；多选行为；在空白处与在选中行上右键，菜单内容是否合理区分；选中后工具栏/状态栏是否有联动反馈。
8. **表格与树**：列宽策略（固定/拉伸/内容自适应）是否合理；排序指示；斑马纹与网格线；表头样式；空数据占位；大数据量下的加载与滚动表现（静态可判定的部分）。
9. **对话框**：是否统一使用 `ui/confirm_dialog.py` 与 `ui/dialog_buttons.py`，还是各 panel 自造；按钮顺序与文案（确定/取消的位置与措辞）；默认焦点按钮；尺寸、居中、模态行为一致性。
10. **反馈与状态呈现**：加载态（`ui/aurora_progress.py`、`ui/thinking_indicator.py`）的使用是否统一；成功/警告/错误提示的样式、位置、文案风格；空状态页面；禁用态的理由提示。
11. **图标与文案**：图标是否统一出自 `ui/icons.py`、尺寸与风格是否一致；界面文案语气、标点、中英文混排空格、省略号用法；tooltip 覆盖率（图标按钮必须有 tooltip，逐个查）。
12. **响应式与 DPI**：`ui/layout_metrics.py`/`ui/responsive.py` 的响应模式是否被各 panel 真正落实；125%/150% 显示缩放下的错位与截断风险；高分屏图标清晰度。
13. **双端一致性**：同一语义元素（按钮、卡片、标题、状态色）在 Vue 前端与 PyQt 侧的颜色、圆角、间距、字号是否一致，列出不一致点。

## 每条问题的格式（缺一项视为无效条目）

- **位置**：`文件路径:行号`
- **现状**：引用关键代码或写明当前数值（如"左 margin=7、右 margin=13，与同页其他组不一致"）
- **问题**：为什么不合理，对照的是哪条基准（设计令牌名 / layout_metrics 刻度 / 企业级通行做法）
- **改法**：给出具体数值或应改用的令牌/公共组件名，能直接照着改，不许写"建议优化间距"这类空话
- **处理结果**：已改＋所在提交短号；或未改＋原因（需用户拍板 / 需运行确认 / 超出 UI 层范围）
- **级别**：P0＝影响可用性/明显错位截断；P1＝一致性硬伤；P2＝打磨项

## 报告必须单列的两节

1. **《设计系统执行情况》**：给出可核查的统计——硬编码颜色数、绕开令牌的 `setStyleSheet` 散落点数、硬编码尺寸点数、绕开公共组件自造轮子的清单（按文件汇总计数），并判断设计系统本身是否够用（令牌缺失导致大家不得不硬编码的，也要指出来，这是设计系统的账，不是 panel 的账）。
2. **《企业级差距与遗留项》**：对照企业级桌面应用在设计令牌完备度、交互状态完备度、键盘可达性、动效规范（`ui/motion.py` 的实际使用率）、错误与空状态规范上的要求，列出差距；本轮能改的已经改掉，剩下的是本轮不适合动或需要用户拍板的，逐条写明卡点。

## 红线（改代码的边界，比审阅更重要）

- **只动 UI 呈现层**：布局、间距、尺寸、样式、状态、文案、tooltip 可以改；业务逻辑、数据处理、接口调用、信号的业务含义**一律不许改**。拿不准是不是业务逻辑的，记为"未改，需用户拍板"，不许赌。
- 在新建分支 `ui-enterprise-polish`（基于 `MuseBulid`）上干活，**不许直接在 MuseBulid 或 main 上改**；每个文件改完单独提交一次，提交信息写明文件名和整改要点；**不推送任何分支**，推送与否用户验收后定。
- 改完每个文件，按 `AGENTS.md` 跑对应的验证（Python 改动跑相关 `python -m unittest tests.test_<area> -v`；动了 frontend 跑 `npm --prefix frontend run typecheck`，涉及内嵌资源再跑 `build:embedded` 与 `verify:embedded`）；测试不过就回退该文件的改动并在报告里如实记录，不许带伤提交。
- 不碰用户 data、真实配置、凭证；遵守 `AGENTS.md` 的分层与安全规则；改动只许 traceable 到本任务，发现的无关缺陷写进报告，不顺手修。
- 静态能定的才下结论、才动手改；需要运行起来才能确认的现象（如某窗口在某分辨率下是否真的溢出），**不要盲改**，标注"需运行确认"并给出复现条件，列入验收清单交用户实机确认。
- 不许用"整体较好""个别地方"这类模糊表述搪塞，每个维度都要落到具体文件和行号。
