# Linux 运维 AI 助手：持续观察、自动取证与排查报告

日期：2026-10-29。状态：产品及技术设计基线；2026-10-30首批源码实现及验证见[实现记录](LINUX_OPS_AI_IMPLEMENTATION_2026-10-30.md)，未交付项以该记录为准。用户最新目标：除历史日志和实时日志外，让大模型参与 Linux 系统监控、异常排查和文档整理。本文扩展 [日志重设计](LOG_ANALYSIS_REDESIGN_2026-10-29.md)，不取消历史文件分析需求。

源码依据：本地 `main / 998d1d76e3ff25bc431e3deeeac73a3f4f35e899` 加未提交修改。`tools/ops_ssh.py` 已有服务器配置和SSH连接；`tools/ops_commands.py` 已有系统状态、systemd及journal命令目录；`tools/log_analysis/` 已有增量日志采集、事件和Agent分析。命令目录存在不代表已具备系统指标采集、告警规则或持续巡检调度。

## 1. 最终使用体验

用户选择服务器、关注的服务及日志，点击“开始监控”。页面持续显示CPU、内存、负载、磁盘、关键服务、进程和端口。异常发生后，程序保留现场并形成事件；开启AI自动分析时，Agent在本任务范围内自动查证，给出结论和处理建议。用户可随时追问“刚才为什么变慢”“这个报错跟磁盘是否有关”，并生成阶段报告。

监控采样和规则判断由程序执行，模型只在异常、显著变化、主动提问或报告请求时工作。模型慢、断网或不可用时，采集、趋势与事件仍应继续；不按每个采样周期把所有指标和日志发送给模型。

## 2. 入口和页面结构

保留现有侧栏“日志排查”，页面标题调整为“日志与系统排查”，暂不扩展全局导航。

顶部三个页签：**人工排查｜历史日志分析｜实时监控**。

- 历史日志分析沿用独立文件选择和有界扫描。
- 实时监控包含 **系统资源／服务与端口／实时日志** 三个视图，共享当前监控任务和AI助手。
- “任务记录”是任务管理入口，单独标注历史扫描或实时监控，不混同历史文件。

```text
日志与系统排查   [人工排查] [历史日志分析] [实时监控]    [任务记录]
──────────────────────────────────────────────────────────────────────
服务器：测试环境A  连接正常  上次采集10:42:10  [配置监控项] [暂停] [停止]
CPU 22%    可用内存3.2GiB    负载0.8/1.2/1.1    磁盘72%    异常2项
──────────────────────────────────────┬───────────────────────────────
[系统资源] [服务与端口] [实时日志]       │ AI运维助手  [内网模型]
指标趋势／服务状态／日志视图            │ 自动分析新异常 [开关]
──────────────────────────────────────│ 当前目标及证据时间
异常事件：级别、对象、首次、持续、状态  │ 正在检查：进程资源 → 相关日志
选中事件：指标证据、日志、取证时间线    │ 事实 / 推断 / 待验证事项
                                      │ [提问] [发送] [停止本次分析]
──────────────────────────────────────┴───────────────────────────────
覆盖：CPU/内存/磁盘/指定服务；journal无权限    [生成阶段报告]
```

状态条同时展示“连接”“采集”“AI”三个状态，不能把人工终端的未连接状态套到监控任务。未知指标显示“无法采集＋原因”，不能以0或绿色正常代替。远端时间、客户端采集时间分开记录，时钟不一致时提醒关联结果存在偏差。

## 3. 配置监控任务

每个任务绑定一台服务器，可配置多个关注对象；首版并发仍限制最多4个活动任务，单主机最多1次系统采样在途，不叠加未完成轮询。

### 基础配置

1. 服务器：复用现有配置，连接前核对主机身份。无需把密码或密钥交给模型。
2. 监控项：系统资源默认开启；用户选择磁盘挂载点、systemd服务、进程、监听端口和日志文件。
3. 进程标识：优先服务PID或明确可执行文件标识；支持进程名但标明同名进程数。PID变化不能简单认作旧进程恢复。
4. 日志起点：从现在开始，或补读末尾指定行数；目录需浏览到文件。
5. 模型：沿用已配置内网模型。启用自动分析视为允许在当前目标范围内执行只读取证，不为每个查询重复确认。

### 高级配置

采集间隔、指标阈值、持续时长、恢复阈值、异常合并、AI冷却、上下文行数、证据额度。启动后界面固定任务范围；修改服务器或服务范围需新任务，避免混用证据。

## 4. 首版监控能力与取证边界

| 监控对象 | 常规采集 | 出现异常时AI可自动补查 | 解释边界 |
| --- | --- | --- | --- |
| CPU | 两次系统计数差值得到使用率 | 资源占用较高的进程、负载、同时间日志 | 首次样本为预热；不能单凭高CPU断言死循环 |
| 内存/交换区 | 可用内存、总量、交换区占用 | 重点进程RSS、OOM相关可读事件 | 缓存不直接算泄漏；RSS增长只提供线索 |
| 系统负载 | 1/5/15分钟负载、逻辑CPU数量 | 可运行/阻塞进程计数与资源指标 | 负载与CPU使用率分别展示 |
| 磁盘 | 选中挂载点空间及inode使用情况 | 选定日志目录的有界文件大小清单、相关I/O错误 | 不自动递归扫描整盘；超时返回部分结果 |
| 服务/进程 | 指定服务状态、关键进程是否存在 | 退出状态、启动时间、有限服务日志、进程资源 | systemd不存在时用已配置进程观察，不假装查过服务管理器 |
| 端口 | 选定监听端口是否存在 | 关联进程（有权限时）、有限连接统计 | 监听正常不等于业务健康；远端连通性与本地监听分开 |
| 日志 | 文件增量、ERROR/异常堆栈；WARN可选 | 前后文、同任务traceId、同一故障窗口相关事件 | 文件轮转、日志淘汰、权限不足均注明覆盖缺口 |
| journal | 有能力且有权限时读取指定服务及错误事件 | 相关故障窗口的服务退出/OOM等证据 | 只查询必要字段；无权限时不自动sudo |

常规采集建议5秒，磁盘30秒，日志2秒，均为初始配置、待内网压测定标。首版不依赖远端安装常驻Agent；登录账号具备什么读取能力就采集什么。

先进行只读能力探测：Linux/proc可用性、SFTP、systemd、journal、基础命令及输出格式。以结构化字段和固定解析器为主，固定locale避免本地化输出误解析；缺失能力有明确降级，不能让模型临时安装工具。

采集命令逐项超时、取消、限输出；网络或挂载点卡住时，其他可用指标继续返回。SSH连接池和会话归任务所有，停止不影响人工终端。读取权限错误和服务停止状态要区分，命令非零退出码不能一概视为采集失败。

## 5. 事件触发、恢复与AI节流

规则不是生产SLA，下面仅是可编辑的首启示例：

- CPU≥85%持续60秒触发；≤70%持续60秒恢复。
- 可用内存≤10%持续60秒触发；≥15%持续60秒恢复。
- 所选磁盘空间或inode使用≥85%持续两次采样触发；<80%持续两次恢复。
- 关键服务或端口连续两次有效采样异常触发，连续两次有效恢复再标记恢复；SSH断开属于采集失联，不能推断全部服务已停止。
- 日志按堆栈指纹、服务和错误码聚合，同类重复仅更新计数；新类型或显著变化触发分析。

每项规则的持续时间仅计算有效样本区间，采集缺失不能当成持续正常或异常。指标计数回退、机器重启、时钟调整需重置相关计算窗口。

事件生命周期：**待确认 → 异常持续 → 已恢复**；用户“已读/已处理”是另一个字段，不能把人工处理当成系统恢复。

AI触发条件：首次异常、严重度升级、关键证据变化、恢复后的总结、用户主动提问。默认同类事件60秒冷却、单并发请求；队列合并同一事件，只保留最新取证请求。证据采集不依赖模型队列。高频异常累计次数并提示积压，不循环输出相同长文。

## 6. Agent如何查证

每次分析固定服务器、服务范围和时间窗口；允许工具仅由宿主提供，参数和目标在模型之外校验。

建议工具：`get_host_snapshot`、`get_metric_window`、`list_monitored_services`、`read_service_state`、`list_process_summary`、`read_process_resources`、`read_disk_usage`、`read_listening_ports`、`list_events`、`read_event`、`search_logs`、`read_log_context`、`read_service_journal`。

- 工具返回值必须包含取证时间、对象、单位、覆盖范围、是否截断及错误类型。
- 常规指标低成本采集；进程详情、journal和上下文按异常触发有界补查。默认不读取进程环境变量和完整命令行，避免采集凭据。
- 既有 `tools/ops_commands.py` 可作为人工展示目录，但其中有修改类命令，不能整个注册为Agent可调用工具。
- 不开放任意shell执行入口来规避工具边界。参数作为受校验的参数处理；不拼接模型生成的管道、重定向、命令替换或脚本。
- 首版只有查询工具；安装工具、清理磁盘、修改配置、kill、启动/停止/重启服务均不自动执行。

示例：服务超时 → 获取故障前后资源窗口 → 查看指定服务进程和端口 → 补查错误堆栈与关联日志 → 列出事实和候选原因。只有找到对应证据才能说“与磁盘空间不足有关”；仅同时发生时写“时间相关，因果未确认”。

同一回答允许引用多个采样时刻，但必须标明取证时间；不能把恢复后现场当作故障当时的状态。持续保留有界指标趋势及异常前后窗口，模型只接收统计摘要和必要片段。沿用500 KiB应用预算及模型实际限制，超预算压缩保留对象、规则、证据ID和待办。

## 7. 修改操作的确认规则

遵循用户既有要求：查询无需逐次确认，新增、修改、删除及改变运行状态的操作必须先确认。首版输出“建议处理”与可复制命令，执行能力作为后续独立交付，不能只加确认按钮就接通任意shell。

若后续接入执行，必须先展示具体主机、服务、确切命令或文件差异、影响和可用回退方式。用户确认绑定这一次具体动作，目标或内容改变后重新确认；不把“同意分析”当作修改授权。操作失败或结果未知不能自动重试。执行后重新查询验证，记录结果，不能因命令返回成功就宣布业务恢复。

## 8. 长期任务、报告与退出

- 一键巡检：选择监控项，采集有限样本并生成概况；CPU需足够样本才有使用率。巡检结束后仍可追问。
- 持续监控：软件运行期间采样，暂停/断线/休眠都明确标记缺口。关闭窗口是否保留任务必须明确，退出软件则停止任务并释放连接。
- 软件重启后只展示上次任务和覆盖缺口，手动恢复，不自动重新连接生产环境。
- 定时报告可作为运行中任务的可选设置：先支持手动生成，之后支持例如每小时生成摘要草稿；这不是Codex自动化或操作系统后台服务。
- 报告包含目标、实际监控项、时间/时区、有效采样占比、异常起止与恢复、资源趋势摘要、日志证据、分析版本、处理建议和缺口。自动草稿不覆盖人工编辑版本。
- 若用户需要软件关闭后仍24小时采集，应另设计Linux端常驻采集服务和留存机制，当前桌面任务不能承诺此能力。

## 9. 实施拆分

1. 完成历史日志与实时模式分离、证据可在采集结束后分析，沿用日志重设计的第一批验收。
2. 建立 `tools/ops_monitor/`：数据契约、Linux能力探测、指标采集、规则与事件。纯业务代码不导入界面。
3. 由任务协调层组合系统采样、服务检查和既有日志采集，不把各线程和协议继续堆到 `OpsLogPanel`。独立任务取消令牌，SSH资源归属清晰。
4. 扩展日志Agent的只读取证工具，复用现有模型适配、runner、压缩和诊断日志，避免另起一套模型循环。
5. 在原生实时页加入资源概览、三个结果视图和AI助手，打通异常现场与阶段报告。

诊断日志仅记录任务/采样/工具类型、耗时、字节数、错误码和取消原因。不得把SSH凭据、进程环境、真实日志正文或模型完整上下文写入调试日志。

## 10. 必须通过的验收

- 合成CPU计数两次取差、计数回退、首次样本、内存字段缺失、磁盘与inode分别告警。
- systemd不可用、journal无权限、进程重启、同名进程、端口已监听但业务未验证，均如实展示。
- 连续有效采样触发与恢复、失联期间不计算正常、同类异常去重与AI冷却。
- 模型卡住、无模型、SSH断线、单个指标超时，其他采集与UI停止按钮可用。
- 停止任务释放自有连接，不影响人工SSH会话；采集停止后仍可分析缓存证据。
- 模型试图读取范围外主机、完整环境变量或执行修改命令时，宿主拒绝且给出可读原因。
- 历史日志、实时日志、系统指标三种证据不混淆时间和来源；已恢复事件保留当时的证据。
- 实际4任务负载、内网模型、SSH权限和Linux发行环境验收单独记录。当前仅完成设计，不使用旧日志单测作为Linux监控上线证明。
