# PengToolsHub AI 上下文与工作区使用规范

状态：已确认（用户要求将视频方法用于项目）

更新日期：2026-09-16

适用范围：需求分析、开发、复核与长会话交接；不改变产品业务、运行时架构或 Git 发布规则。

## 1. 目标

Agent 长时间工作后频繁出错，往往不是模型能力不足，而是项目事实、会话过程、重型证据和代码工作区混在了一起。本项目将四类信息分开承载：

| 信息 | 正确载体 | 用途 |
|---|---|---|
| 长期稳定的项目事实 | 固定 Project：仓库内 `AGENTS.md` 与 `docs/project/` | 跨会话保留架构、决定、验收和协作边界 |
| 当前会话的工作状态 | 结构化交接摘要 | 让新会话不重做调查，也不继承无关聊天噪声 |
| 大日志、截图、抓包和研究材料 | 文件系统中的任务证据目录 | 按需搜索和局部读取，不把整份原始输出塞进对话 |
| 并行代码实现 | 独立 Git worktree | 隔离会同时修改代码的方案或代理 |

优化目标不是单次提示词最短，而是完成整个任务所需的总成本：压缩后若必须重复读文件、重新定位问题或重新确认决定，说明交接丢失了关键信息。

## 2. 固定 Project 是长期办公室

每个 PengToolsHub 任务继续从 [项目入口](README.md) 开始。稳定信息只写到对应的权威文件，不把聊天记录当作项目记忆：

- `AGENTS.md`：耐久工程边界与安全规则。
- `docs/project/README.md`：当前入口、产品决定和文档路由。
- 模块需求/交接文档：具体范围、源码证据、验收状态和未完成项。
- `docs/ui/prism-implementation-*/` 等任务证据目录：与一次实现直接相关的截图和报告。

新增内容前先确认现有权威文件；能更新原文就不再创建“最终版”“修订版”副本。聊天中的新决定只有写回权威文件并标明状态、日期和范围后，才可作为后续会话的稳定依据。

## 3. 长对话何时交接

出现任一情况就应在继续实现前生成交接摘要：

1. 工作从调查进入实施、从实施进入验证等明显阶段边界。
2. 同一事实被重复查找，或者开始混淆已完成、计划中和待验收状态。
3. 用户切换任务，但原任务仍需稍后继续。
4. 当前会话已经包含大量日志、截图说明或多轮返工，继续追加会明显降低可核验性。
5. 需要把工作交给另一个会话、代理或只读 Git 审阅者。

不要仅写自由散文。交接必须使用以下结构，并逐项核对源文件、Git 和测试输出：

```markdown
## 任务目标与范围
## 仓库状态（分支、完整 HEAD、远端比较、已有未提交改动）
## 已确认决定与不变契约
## 已读证据与最短调用链
## 已修改文件（路径 + 符号/区域 + 改动目的）
## 验证（命令、结果、环境；失败/跳过/未运行分开）
## 当前状态与未解决风险
## 下一步（首个可执行动作 + 禁止顺带修改范围）
```

交接摘要采用增量维护：只合并本阶段新增事实，不反复重写整份历史。分支、SHA、路径、函数名、错误文本和数值保持原样；不能凭记忆补全。原始证据仍保留在文件中，摘要只提供结论与定位指针。

## 4. 重型上下文外置

以下内容默认写入任务对应的证据目录，再在对话或交接中给出简短结论和相对路径：

- 超长构建/测试日志、抓包结果、数据库查询输出。
- 批量截图、运行时快照、原型资源和审计原始结果。
- 大型网页/文档研究材料，以及需要反复检索的对照表。

执行规则：

1. 复用现有任务目录；不要把临时输出散落在仓库根目录。
2. 文件名包含任务或阶段含义；原始证据与由其得出的报告放在一起。
3. 后续读取先用精确文件搜索和关键词定位，再读取相关区段，不默认加载整个目录。
4. 敏感数据、凭据、真实用户数据和生产 payload 不得因“外置”而写入仓库。
5. 临时材料不需要版本化时，放在仓库外的临时目录并在交接中说明生命周期；可复核交付证据才进入仓库。
6. 提交前检查体积、来源、脱敏和必要性，删除只属于本任务且已失效的临时副本；不得清理用户或其他任务的文件。

## 5. Worktree 的使用边界

默认在当前用户指定工作区顺序完成一个逻辑任务。只有以下情况使用独立 worktree：

- 两个或更多代理/方案需要同时修改代码，且改动可能重叠。
- 用户明确要求并行实现或保留多个可比较方案。
- 长时间实验必须与当前未提交工作隔离。

以下情况不使用 worktree：阅读、总结、单一路径的顺序开发、只跑验证、为了“环境整洁”而复制仓库，或把 worktree 当作对话记忆。

每个 worktree 必须记录基线提交、负责人/方案、允许修改范围和集成方式。不同工作区不得同时承担同一文件的权威编辑；合并前分别验证并检查目标分支是否移动。创建 worktree 不授权自动切分支、合并、变基、清理、强推或覆盖用户已有改动。

## 6. 开始、续作与结束检查

### 开始/续作

- 从 `docs/project/README.md` 路由到当前模块，只加载有关文件。
- 核对实际分支、完整 HEAD 和工作区状态，不把上次交接中的 Git 状态当成当前事实。
- 若有交接，先验证其中的路径、提交和未完成项仍有效，再执行“下一步”。
- 大材料按需检索；不要因为它曾经被读取，就在每轮重新加载。

### 结束/交接

- 更新权威需求/状态文件，不只在聊天里宣布完成。
- 列清创建、修改、只读文件和未跟踪证据，保证 artifact trail 可追溯。
- 报告实际验证与未验证项；构建、运行、视觉和用户验收不得互相代替。
- 若任务尚未完成，写出首个可执行下一步；若已完成，说明提交/推送状态和仍需用户验收的边界。

## 7. 交接质量自检

新会话应能仅凭项目入口、交接摘要和所指文件回答以下问题；任一不能回答，就补齐交接而不是让下一会话重新探索：

1. 用户最终要什么，哪些内容明确不在范围内？
2. 当前实际分支、HEAD 和已有未提交改动是什么？
3. 哪些是已验证事实、批准目标、实现中内容和待验收项？
4. 修改了哪些文件与符号，为什么？
5. 哪些验证通过、失败、跳过或尚未运行？
6. 下一步是什么，最大的风险或阻塞是什么？

本规范落实的是工作边界与信息载体选择。它不替代模块需求、源码审查、定向测试或用户视觉验收。
