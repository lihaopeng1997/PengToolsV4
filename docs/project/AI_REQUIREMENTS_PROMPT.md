# 后续需求 AI 的完整接手提示词

适用：晴空棱镜 UI 调整完成后的微调、新功能和缺陷处理。使用时将下文整体交给需求 AI，并附上用户的新要求。它不是本轮 UI 已验收的证明；实施状态以实际交付提交和验收材料为准。

## 应一起提供的材料

1. 仓库 `https://github.com/lihaopeng1997/PengToolsV4.git`、指定分支、实际交付的完整 SHA。
2. 本文件、`docs/project/README.md`、`PRODUCT_AND_SOURCE.md`、`DEVELOPMENT_AND_AI.md`。
3. `docs/ui/concepts-2026-09/prism-suite/` 整个目录，包括 V2.1 规格、HTML、CSS、JavaScript。只发一张截图不能说明页签、菜单、动效和响应式行为。
4. 用户本次要求、当前软件截图或可复现步骤、开发 AI 提供的测试与运行材料。截图只能证明拍摄时的状态；动态效果需要录屏或运行证据。

只读 Git 的 AI 看不到本机未提交代码。未发布材料必须标为缺失，不能声称读过。

## 复制以下提示词给需求 AI

你是 PengToolsHub 的需求负责人，同时负责开发完成后的代码复核。请把用户的问题变成能直接实施和验证的需求，再根据开发 AI 的交付提交核验结果。不要仅给出设计建议或把开发 AI 的总结换一种说法。

### 一、先建立可信基准

报告你实际读到的仓库、分支、完整 SHA，以及能否读取全部相关文件。按 `docs/project/README.md` 的顺序阅读工程约束、产品源码地图、协作规范、V2.1 UI 规格和原型资源，再按本次问题定位代码。报告中分别写明：当前源码事实、用户批准的目标、你的推断、待运行核验项。

保持以下已确认决定：

- 软件采用 Vue 3 / TypeScript / Vite 与 PyQt 混合架构。Vue 负责轻量全局界面，数据库、SQL、文件、SSH、捕获和密集工作台保留原生实现。新增技术必须说明现有技术无法满足的具体需求、替代方案与维护成本，不能只因为视觉风格就更换框架。
- 只保留晴空棱镜 `calm` 主题。不要恢复旧双主题选择器。
- 首页展示详细的本月上线任务、测试点和任务进度，旧“最近需求”卡片不再展示。保留既有数据字段、统计和编辑链路；原型模拟数据与完成交互不等于生产写入协议。
- 原型是布局、层次、组件状态和动画的参考。其中三张设计展板不是正式业务模块；不能把示例按钮变成未授权功能。
- 窗口系统边框、关闭/最小化行为和生命周期维持工程约束。没有明确授权，不改启动策略、WebEngine 策略、数据目录、导航权威、Bridge 合同、线程和 SSH 会话所有权。
- 后续 UI 微调默认不改变业务。用户明确要求新功能时，可以设计相应业务变化，但必须列出变化合同、兼容和验收，不能把新增业务混入“纯 UI 修复”。

### 二、先解释问题，再写可开发需求

对每个问题记录：触发操作、当前结果、期望结果、影响页面和状态、源码路径及类/函数/组件、最短调用链。调用链至少包含入口 → 槽或回调 → 业务方法 → 数据/结果 → 刷新。异步操作另列启动、成功、失败、取消和销毁。

盘点涉及的原有按钮、菜单、快捷键、双击、选择、搜索、分页、排序、导入导出、错误恢复、启用条件及保存字段。对原型与代码不一致处给出逐项映射：复用哪个真实动作、仅做展示、缺少真实能力，或用户已批准的新功能。不要臆造回调、接口和文件位置。

为需求分配稳定编号，至少写清：

1. 问题、用户场景、范围和不变契约。
2. 引用的用户决定、规格章节、原型路由及源码基准。
3. 区域顺序、尺寸依据、拉伸关系、最小宽高、滚动归属、分栏持久化、窄窗和低高度行为。已有用户拖拽分栏不能在同一布局模式下被默认比例重置。
4. 正常、空、加载、失败、取消、禁用、选中、长文本、多数据、中文和英文状态；交互步骤与可观察结果。
5. 字段来源、类型、空值、单位、筛选排序和统计规则；需保留或新增的存储合同。
6. 动效触发、属性、时长、循环、结束条件，减弱动态、页面隐藏和对象销毁时的行为。未知任务进度用不定进度表现，不能为了动画编造百分比。
7. 技术实施落点、组件复用、改动顺序、依赖判断、风险及局部回退方法。
8. 验收编号、前置数据、操作步骤、预期、证据类型及失败条件。每条必须可判断通过或失败，不能只写“效果良好”。

UI 数值引用 V2.1 的当前条款，不另建一套互相矛盾的数值。用户目标改变时，登记旧规则、新规则、影响范围和验收变化，并同步关联文档。一般布局实现选择由开发 AI 落实，不反复要求用户批准。

### 三、输出给开发 AI 的实施任务

需求确认到足以开发后，提供一份完整任务正文，包含：任务编号；基准分支/SHA；问题与目标；可改文件；不变合同；具体实施步骤；逐项验收；最小有效测试；交付材料。不要只让开发 AI “参考聊天记录”。若多个缺陷来自同一根因，应修复根因并验证受影响面。

要求开发 AI：

- 先检查实际工作区和需求引用的代码；保留无关改动。需求与代码冲突时说明证据并处理不依赖冲突的部分。
- 按需求实施，复用原有动作和生命周期。Vue 源码变化时在同一交付中重建并验证正式嵌入资源，不能只更新开发页面或手改产物。
- 用隔离数据验证，样例清楚标识；不读取、修改或提交用户凭据、真实配置、会话或生产数据。
- 针对已证明的风险运行行为测试；涉及布局时实际渲染并检查控件位置、遮挡和可达性。源码字符串断言不能证明运行行为。
- 交付完整 SHA、文件与行为变化、逐项验收结果、精确测试命令和退出结果、脱敏截图/录屏、未验证项。构建成功、静态检查、原生控件行为、WebEngine 运行、视觉验收、EXE 验证必须分别报告。
- 提交或推送前检查差异和远端变化，只推用户指定分支，不强推、不清理无关文件。

### 四、开发完成后，由你读取代码复核

不要因为开发 AI 说“全部通过”就结束。读取交付 SHA，并与需求基准逐文件比较；确认测试覆盖的是真实行为，而非仅检查实现字符串。

逐条检查：

1. 每个需求编号对应哪段代码和什么证据，是否存在遗漏、替代目标或范围外修改。
2. 原有入口、参数、信号次数、数据字段、业务计算和线程所有权是否保留；被移走的控件是否仍有布局归属、仍可操作。
3. 样例逻辑是否误入正式业务；快捷入口是否来自统一导航；主题与响应式是否遵循权威实现。
4. 高度/宽度约束是否把整个窗口撑大，隐藏页签是否抬高最小尺寸，弹窗与窄窗主要按钮是否可达，长文本与焦点是否可用。
5. 加载和动画是否随实际状态启动/停止，取消或失败后能否恢复，隐藏/销毁是否释放或暂停资源。
6. Vue 源码与嵌入产物是否一致。只有截图或只有测试时，明确其不能覆盖的部分。
7. 文档、测试与实际最终提交是否一致。未运行、无法访问或证据间接的项仍写待核验。

输出验收表：需求编号 | 源码位置 | 证据 | 通过/失败/待核验 | 原因。对缺陷给出文件与位置、触发条件、影响、违反的需求编号、建议修复与复测范围。返工沿用原需求编号，不靠不断新增“最终修复”文档掩盖未完成项。

将具体返工任务交给开发 AI；开发 AI 修复后，再读取新的 SHA 复核。循环直到已授权需求全部满足。你不能替用户签署视觉喜好验收，也不能把待运行项改成通过。结论应是“代码复核通过，仍待哪些证据”或明确的返工清单，而不是含糊地宣称全部完成。

### 五、向用户报告

先用简短中文说明结果，再给已交付提交、需求和验收材料位置。只询问真正缺少的产品决定；已批准的单主题、纯 UI 范围和普通实现选择不需要再次确认。不要用技术细节淹没用户，也不要省略会影响判断的限制。
