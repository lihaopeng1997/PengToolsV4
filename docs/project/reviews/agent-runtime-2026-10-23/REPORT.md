## 已确认的问题与修复

| 问题 | 当前处理 |
| --- | --- |
| 数据库旧 AI 入口只给 SQL / Redis 命令 | 旧入口的系统提示明确要求只生成、不执行。SQL、Redis、MongoDB 工作台隐藏该旧页签，统一使用只读 Agent；对象详情的“发送到 AI”也接到新入口。草稿模式仍可明确选择。 |
| 数据库每轮丢失上下文 | controller 把完成后的规范消息记录返回宿主，下一轮继续携带；连接、模型、Schema 范围变化后清空模型上下文，新建对话同时清空显示记录。运行期间目标不可变。 |
| Oracle / OceanBase 查询范围太宽 | 成功扫描后可在“查询范围 · Schema”选择用户/Schema，默认优先当前登录用户或唯一 Schema，否则列出全部已扫描范围。所选范围进入真实元数据与 SQL 宿主策略，不能靠模型自行换库越界。 |
| 聊天框显示工具 XML / JSON | 按完整流式轮次过滤协议，兼容原生工具、显式正文工具标记、完整 JSON 工具信封；不从普通 SQL 文本猜测并执行命令。答案按 Markdown 展示，工具证据折叠。 |
| 输入与布局混乱 | 数据库使用单一聊天滚动区，固定输入框；Enter 发送，Shift+Enter 换行，输入法组合期间不发送。工作台发送后的滚动等待布局完成，用户手动翻阅旧消息时保持位置。 |
| 读取结果被脱敏破坏 JSON | 编程工具先逐个字符串脱敏，再序列化，避免正则吞掉转义后的 JSON 结构。 |
| 查询被策略拒绝后误报 worker 仍在运行 | 只清理尚未派发的 expected 查询；不清理实际运行 worker 的 pending 状态。 |
| 60 秒后读代码“卡住” | 用户提供的日志显示超时前仍持续收到模型数据，客户端旧 60 秒总时限是直接中止条件，不能据此认定模型服务故障。现在分为空闲超时和总时限，见下表。 |
| 写入权限规则不一致 | 按用户最新要求：读取、搜索、目录、SVN status/diff 无需确认；创建、覆盖、编辑、删除、SVN 提交须展示预览后确认。项目测试会执行项目代码，可能写入文件/数据，也需确认。“先列计划”只展示计划，不再额外审批只读工具。无完全访问绕过开关。 |
| 右键菜单英文或功能不足 | 知识内容查看器、工作台/数据库输入框提供中文复制所选、复制全部、全选；编辑输入区还包含撤销、重做、剪切、粘贴，知识查看器可进入原编辑流程。 |

## 500 KB 与长任务策略

| 层次 | 默认值 / 行为 |
| --- | --- |
| 单次模型请求 | 500 KiB，即 512,000 个 UTF-8 字节；这不是模型 token 窗口的声明。最终序列化请求仍独立检查。 |
| 主动压缩 | 达到约 80%（400 KiB）时尝试压到约 60%（300 KiB）。先裁减旧的完整工具轮次；仍过大时对工具输出、旧回答及必要的旧用户内容做有标记的摘录。 |
| 不变信息 | 原始会话不被截断改写；当前用户请求、系统指令、工具定义和调用 ID/参数不缩写；工具调用与结果始终配对。摘录包含来源长度/哈希，不能当作新的授权或新查到的事实。 |
| 压缩边界 | 摘录不是无损压缩，也不是可靠保留全部细节的语义总结；需要精确代码/字段时重新读取来源。单条当前请求或不可变工具参数本身超过上限仍会停止。服务端 token 窗口未知，500 KiB 不保证服务端必然接受。 |
| 模型连续无响应 | 默认 60 秒，设置可调整到 600 秒；首个数据与后续数据间隔分别受此限制。 |
| 模型单轮最长时间 | 默认 600 秒，设置可调整到 3,600 秒；持续有数据不再被旧的 60 秒总时限打断。显式测试/调用方的短截止时间仍有效。 |
| 编程长任务 | 最多 120 轮、360 次工具调用、2 小时；累计输入/输出额度随轮次分配，避免原来的 4,096 token 累计输出上限提前结束。可随时停止，结束后的原始记录用于“继续”。 |
| 数据库任务 | 默认 30 分钟运行预算；累计输入/输出随 12 轮分配，查询次数、只读策略和结果投影限制继续生效。 |

旧配置键 `agent_deadline_seconds` 兼容保留，但设置里现在明确显示为“连续无响应超时”；新增 `agent_max_turn_seconds` 是单轮总时限。没有修改用户现有配置文件或会话数据。

## 架构判断

目前应保留公共 AgentRunner，把差异放在模型适配和领域工具宿主，不必重写全部 Agent。

```text
工作台 / 数据库聊天
        ↓ 固定任务、连接、Schema、模型配置
公共 AgentRunner（预算、取消、完整工具轮次、事件）
        ├─ 上下文规划：500 KiB 门限 + 请求副本压缩 + 原始记录
        ├─ 模型适配：原生工具 / 严格 JSON / 正文协议 + 空闲与总超时
        └─ 领域工具：编程预览确认 / 数据库只读与范围检查
```

这次修复集中在入口、消息往返、预算和协议适配，均有源码或日志证据。没有新增外部 Agent 框架、云服务或不可控的后台续跑。长任务仍是本机前台任务；没有把“继续”描述为关闭应用后自动后台执行。

千问 3.8 能否稳定驱动完整任务仍取决于内网具体模型变体、服务框架、工具解析配置和上下文窗口。当前日志能力声明为 unknown；本地已验证 unknown 正文标记/完整 JSON、strict_json、native_tools 的模拟工具往返。官方部署参考：[Qwen3.8](https://github.com/QwenLM/Qwen3.8#deployment)。真实内网服务未连接，不能用模拟测试替代验收。

Oracle 与 OceanBase 仍用现有驱动链路。OceanBase 必须匹配实际 Oracle/MySQL 租户模式；包内 Python 模块不代替目标机器上的 ODBC 等系统驱动。
