# Manual-session table source

## Public contract

`ManualSession.open_table_source(tree_service, tree_target, node, *, tree_generation, choice, page_size=None) -> Future[TableSourceOpenResult]` opens one signed relational table or view using the existing manual-session connection and owner. The synchronous request path resolves the signed tree node without DB I/O, verifies the immutable connection choice against the complete manual target, checks the page size (`50`, `200`, or `500`), and queues the owner operation. The owner resolves the same signed node again, checks the captured manual target and choice, inspects bounded provider catalog rows on the manual connection, checks the tree reference again before the table query, and passes a quoted `SELECT` to the existing typed result-page machinery.

`TableSourceOpenResult` contains the page and `TableSourceMetadata`. The metadata preserves the raw table and column names, provider-reported type, nullability, default/generation facts, and ordered primary-key columns. `verified_changeset` is present only for a base table with a verified complete primary key and safe comparable key types. Views and tables without a verified primary key can be browsed but are read-only. Large-object and spatial types are not offered for cell edits in this version. Oracle's database/service remains separate from the signed owner's schema; MySQL's selected database remains the schema. The tree generation/refresh epoch is validated in the tree service's namespace and is never compared numerically with the manual tab generation.

An empty MySQL or OceanBase MySQL `TreeTarget.database` is the signed whole-server tree root. The root itself cannot authorize a table; after the live tree resolver verifies the database child and raw table/view node, the nonempty `ref.database` must exactly equal both the selected `ConnectionChoice.database` and current `ManualSessionTarget.database`. A nonempty MySQL tree-root database remains an exact scope and must match the reference. No database is inferred from a label, profile default, or display text. Oracle roots remain service-bound: their service is captured from the same-revision authoritative profile according to the direct connector's first-present `database`, then `schema` precedence. Explicit Oracle service scope must equal that captured value, and an empty/unrepresentable service is rejected before secret resolution or connection.

The table `SELECT` is created solely from signed raw table identity plus catalog-verified column identifiers and the bound dialect's quoting policy. Catalog values use DBAPI bind parameters. No SQL is reconstructed from display labels, no query is replayed, and the page uses the existing manual connection/cursor and raw typed values. Opening a table does not commit, roll back, create a savepoint, or change a pre-existing `DIRTY` transaction. Catalog cursors are read with repeated `fetchmany` calls capped at 128 rows per call and 1,025 total rows; more than 1,024 columns or key entries fail closed. The result page and continuation use the manual session's existing 50 MiB memory budget and cursor lifecycle.

The owner marks the Future running before its first DB call. A queued Future can still be canceled with `Future.cancel()`; after owner execution begins that returns `False`, and callers must use `cancel_current()`. Cancellation is cooperative. The Future remains pending until the DBAPI call returns, and queued close/cleanup retains the driver until the owner has actually finished.

The public-path regression uses `ObjectTreeComposition` and the production `RelationalReadOnlyHost`, captures the signed Oracle service and schema/table nodes, creates a `BoundManualTableScope`, then opens typed table rows through `ManualSession` and the production relational provider factory on its owner. The fake connector verifies a deliberate `CURRENT_SCHEMA` change and same-connection verification; it does not represent a packaged Oracle driver or a live database.

## Catalog facts and provider limits

MySQL and OceanBase MySQL use fixed queries against `information_schema.TABLES`, `COLUMNS`, and `KEY_COLUMN_USAGE`. The selected database/table/column identifiers are parameters in the catalog predicates; `LIMIT` is bound. Primary-key fields are ordered by their `ORDINAL_POSITION`. The `COLUMNS` query asks for `COLUMN_DEFAULT IS NOT NULL`, rather than fetching arbitrary default-expression text, and uses `EXTRA` for `AUTO_INCREMENT`, generated columns, and `ON UPDATE` facts. MySQL's nullable columns may omit a value because they implicitly default to NULL. A non-null default does not become a required insert value; the regression test feeds the resulting production metadata into `ChangeSet.stage_insert` and verifies that a defaulted column may be omitted while a required no-default column may not.

Oracle and OceanBase Oracle use `ALL_OBJECTS`, `ALL_TAB_COLUMNS` with `ALL_TAB_COLS`, and `ALL_CONSTRAINTS` joined to `ALL_CONS_COLUMNS`. A base table's complete primary key is accepted only when the constraint is enabled and validated, with key columns sorted by `POSITION`. Column order is preserved by the catalog column id; gaps are allowed. Identifiers are returned exactly as cataloged and quoted as one component, including quoted owner/table names.

OceanBase Oracle needs a precise limitation. The official [OceanBase v4.2.0 `ALL_TAB_COLS` reference](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001030467) says its `IDENTITY_COLUMN` catalog field is unsupported and NULL by default. That is evidence about the catalog field, not evidence that the engine lacks identity-column functionality: the official [OceanBase v4.3.0 Oracle-mode foreign-key documentation](https://en.oceanbase.com/docs/common-oceanbase-database-10000000001232651) includes a successful `CREATE TABLE` example with `GENERATED BY DEFAULT AS IDENTITY`. Oracle itself documents `IDENTITY_COLUMN` as a yes/no field in [ALL_TAB_COLUMNS](https://docs.oracle.com/en/database/oracle/oracle-database/26/refrn/ALL_TAB_COLUMNS.html) and exposes identity-column details through [ALL_TAB_IDENTITY_COLS](https://docs.oracle.com/en/database/oracle/oracle-database/26/refrn/ALL_TAB_IDENTITY_COLS.html). The current OceanBase Oracle adapter does not infer identity from default-expression text or sequence naming. It treats generated-column status as unknown and conservatively blocks edits for that source until an authoritative OceanBase-compatible identity metadata route is verified. This is a current capability gap and must not be treated as completion of OceanBase Oracle editing; continue with a verified metadata capability before enabling per-column edits or inserts.

Dameng remains unsupported because a production manual driver/factory and verified catalog capability are not wired. This package does not report Dameng edit compatibility. All five relational targets, including the Dameng follow-up, remain in the overall DC00–06 objective; this backend tranche does not complete table editing or its UI.
