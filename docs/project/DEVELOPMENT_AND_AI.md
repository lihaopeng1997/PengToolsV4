# 后续项目开发规范与双 AI 交接协议

适用于当前晴空棱镜改造及后续迭代。它规定如何从证据形成需求并交付，不代替某个模块的具体业务需求。UI 尺寸、色值与动画参数以链接的 V2.1 规格为准，本文件不维护第二套数字。

## 1. 角色与决定权限

| 角色 | 必须完成 | 不应代替谁做决定 |
|---|---|---|
| 用户/产品负责人 | 确认目标、实质功能变化、视觉取舍、最终验收 | 不必逐个批准普通布局实现细节 |
| 需求 AI | 读取指定 Git 提交，建立现状/目标/差异，输出可开发需求和验收 | 不臆造本地运行结果，不擅自删功能或改变技术路线 |
| 开发 AI | 核对需求与本地源代码，实现授权改动，验证并提供证据 | 不把实现困难直接改写为产品需求，不擅自扩大范围 |
| 审阅者 | 对照差异、行为测试、截图与限制给结论 | 不能用“代码看起来正确”代替用户视觉验收 |

需求 AI 没有读到文件时，应给出精确缺口，例如“当前 SHA 中没有该文档，请提供已提交版本”；不要要求它假装能读取 `D:\PengTools`。开发 AI 收到与当前代码冲突的任务时，应先完成不依赖该冲突的工作，并提出具体替代方案。

## 2. 文档权威与变更登记

每份新需求必须包含状态：草案、已确认、实现中、待验收、已验收、已取代。文档日期不是批准证据。阶段提交标题也不是验收结论。

按以下顺序处理冲突：

1. 核实用户最新明确决定及适用范围，并记录原意。
2. 对照 [项目入口的决策表](README.md) 与当前 UI 规格。已批准变更覆盖旧规范中的冲突条款。
3. 读取当前分支业务源代码与调用链，确定“功能保持”的具体含义。
4. 区分代码缺陷、需求遗漏、批准变更、未实施计划、历史资料；分别处理。
5. 真正需要新增/删除功能、迁移数据或改变架构时，提交具体可评审方案；不能仅为消除文档冲突而直接改业务。

变更登记字段：决定 ID、日期、用户要求、原规则、新规则、影响模块、保持项、需更新文档、验收变化、关联提交。修改主题这种已确认决定时，必须同步原规格的正文与验收矩阵，不能只在聊天中解释。

不得反复新增 `FIX-1/FIX-2` 需求而不记录根因。返工应指向原需求的具体未满足条款和失败证据；若目标变化，登记为需求变更，而不是声称前一个实现始终错误。

## 3. 每项任务的开始步骤

1. 报告仓库、分支、HEAD SHA、远端比较结果及工作区已有改动。不要为“统一环境”自动切 main、拉取合并、清理或重置。
2. 读 AGENTS、项目入口、当前模块需求；按模块地图定位实现。只读与本任务相关的源码。
3. 记录完整最短调用链：入口控件/动作 → 槽或回调 → 工具函数/服务 → 保存或结果 → UI 刷新。异步任务另列开始、成功、失败、取消、销毁。
4. 建立功能清单：按钮、菜单、快捷键、双击、筛选、排序、导入导出、错误恢复、启用条件、语言与可访问性。
5. 列出修改文件与不变契约；确认原型中的每个按钮都有真实动作对应。不存在的原型功能不进入生产。
6. 选最小有效验证，确定哪些需要运行环境或人工截图。无法验证的项提前列出，不能到交付时改名为“已通过静态验收”。

对 Git 只读需求 AI，第1步使用其实际可读取的远端提交；工作区状态由开发 AI 的交接材料提供，不自行推断。

## 4. 可以直接开发的需求模板

每个模块使用下列结构，不要只交“现代、科技、玻璃、好看”等形容词。

```markdown
# REQ-编号：模块与具体目标
状态：草案/已确认；负责人：；更新日期：
仓库与分支：；源码基准完整 SHA：
关联决定：；关联 UI 规格章节/原型路由：

## 问题与用户场景
谁在什么操作中遇到什么问题；当前结果与期望结果各是什么。

## 源码证据
路径 + 类/函数/组件 + SHA；入口到结果的调用链。
事实、推断、待核验分别列出。

## 范围
本期修改的展示面、子窗与状态；明确不变的业务契约。
拟改文件和复用组件；新文件的必要性。

## 页面和交互
区域顺序、尺寸引用、拉伸/最小宽/滚动责任；焦点顺序。
每个动作对应的既有回调、参数、启用条件、调用次数。
正常、空、加载、失败、禁用、选中、长内容、窄屏状态。

## 数据
字段来源、单位、枚举、空值、排序/筛选/统计口径。
模拟数据标识与交互隔离；不得修改的保存字段/兼容规则。

## 动效
触发、目标属性、时长、循环/停止、reduced-motion、隐藏/销毁。
引用公共规格；不能用动画推测真实进度。

## 实施与风险
分步修改顺序；旧控件/线程/连接的保留方式。
依赖是否新增；性能和兼容风险；失败降级与局部回退方法。

## 验收
每条：前置条件 → 输入/操作 → 可观察结果 → 失败判据。
自动验证命令；人工视口/缩放/截图；环境依赖与未验证项。

## 交接
变更文件、实现提交、测试证据、截图、遗留项、下一任务边界。
```

## 5. 布局、组件与图标实施规范

主窗宽 W 与内容宽 C 必须分别说明；C 是扣除导航和外层边距后工作区宽度。不得拿 W 的断点判断 C，也不得在每个模块新建一套布局阈值。公共规则由 `layout_metrics.py` 负责，页面自己的子区域阈值需在需求中标注测量对象。

先指定区域的最小宽、伸展权重、最大宽和滚动责任，再放控件。长表格可以横向滚动，整个主窗口不应因固定大卡片横向溢出。文字行数不固定的卡片使用最小高度和自然增高；缩放不能靠裁掉文字解决。

统一使用语义主题、图标角色和公共按钮/输入/提示组件。数据库编辑器、终端与状态颜色保留专用语义，不因单一浅色主题强行让所有内部背景完全相同。选中、错误与完成状态不能只靠颜色传达。

图标展板用于校验笔画、尺寸和语义，不是新增菜单。每个业务动作应能追溯到原有回调；图标换位置后 tooltip、键盘入口和可访问名称仍有效。系统非客户区、托盘和浮窗拖拽行为继续使用既有机制。

悬浮框收起为规格中的单图标入口；展开的工具、聊天、学习及设置遵守现有可达性和权限。不得为了动画流畅吞掉点击，或者因尺寸改变丢失多屏位置恢复。实现细节以 V2.1 与当前 `quick_panel.py` 的生命周期为准。

## 6. Loading 与异步状态规范

| 状态 | UI 要做什么 | 业务约束 |
|---|---|---|
| 空闲 | 原内容和操作正常可用 | 不创建额外后台轮询 |
| 已请求但未达到展示阈值 | 沿现有延迟避免闪烁 | 不推迟真正发起任务 |
| 不定进度加载 | 使用统一动画/文字，保留允许查看的旧结果 | 不编造百分比 |
| 有真实进度 | 显示既有进度数据及文字 | 不改进度取值、单位或回调接口 |
| 成功 | 按原完成事件更新结果、结束加载 | 动画结束不是成功依据 |
| 失败 | 显示原错误与已有恢复入口 | 不能假装成功或把失败变成空列表 |
| 取消/关闭 | UI 动效清理；沿原取消路径 | 不擅自中断或继续原业务任务 |
| 隐藏/减弱动态 | 暂停装饰循环或使用静态状态 | 任务仍按原逻辑运行 |

公共 Loading 的延迟、最短显示、linger、并发任务身份与迟到完成保护以现有接口及 V2.1 第10节相关条款为准。不得在某页新加一个独立定时器模拟“已完成”。聊天首字等待与流式生成是不同状态，必须沿实际事件切换。

必须测试：短任务不闪烁、长任务有反馈、A/B 重叠任务迟到回调不误关 B、失败打断等待、真实进度、切页销毁、减弱动态和旧结果保留。只看动画截图不构成这些行为的验证。

## 7. 源码与资源交付

Vue 改 `frontend/` 源码；正式入口在 `resources/webui/vue/`。同一交付包含生成后的资源新增、删除和入口引用；禁止手改压缩 JS/CSS。生成前先确认目录只用于构建产物，不能扩展清理范围。

Python 依赖方向保持 `run → main_window → panels → tools / ui / config`。UI 元数据需要进入汇总时由调用方注入；不要让 `tools` 导入 `ui`，也不要让 Bridge 导入具体面板。复用既有实例和信号，不重复连接，不 monkey patch 全局控件行为。

公共组件改动先确认所有调用者；模块改造先做一个代表性页面并验证复用边界，再推广同类页面。不是所有页面都适合统一成卡片：SQL、对象树、日志和终端保留信息密度及快捷操作。

## 8. 验证层次与报告格式

| 证据 | 能证明 | 不能证明 |
|---|---|---|
| 源码/差异审阅 | 修改范围、依赖、预期路径 | 实际运行成功、视觉合格 |
| Typecheck | Vue/TS 类型一致性 | DOM 交互、Qt 渲染、业务正确 |
| build + verify:embedded | 构建成功、入口资源引用与离线约束检查 | 屏幕无裁切、点击仅触发一次 |
| 业务/面板定向测试 | 被测输入和行为契约 | 全部功能和实际网络目标 |
| 真实 WebEngine 集成测试 | 目标环境中被覆盖的 Bridge/DOM 行为 | 用户对整套 UI 的视觉接受 |
| 人工运行截图/操作 | 标明环境和页面的布局/交互证据 | 未展示页面与所有异常路径 |
| 安装包烟雾 | 对应包在对应机器的启动/资源验证 | 其他机器、业务全量正确 |

常用命令（每条检查退出码，前一步失败不能因后一步成功而覆盖）：

```powershell
npm --prefix frontend run typecheck
npm --prefix frontend run build:embedded
npm --prefix frontend run verify:embedded
python -m unittest tests.test_dashboard_summary -v
python -m pytest -q tests/test_prism_drift_repair.py
git diff --check
```

命令按实际改动挑选，上例不是所有任务强制全跑。涉及 WebEngine 时另运行相关集成测试，原生 Qt 测试优先按文件隔离进程。进程崩溃、空输出或被跳过一律不能记为通过；记录退出码、环境、复现命令，区分本次引入与尚未归因，禁止未做基线对比就称“原有问题”。

视觉验收按 UI 规格矩阵，至少覆盖本任务的正常/空/错/忙、窄宽、长中文、英文和缩放；记录视口与 DPI。无需每次小修都全量打包和测试整个项目，但最终 P10 必须覆盖全部约定展示面。测试夹具必须脱敏且与用户数据隔离。

## 9. Git 交接和远端可读性

一个逻辑任务形成一个可审阅差异，通常一个提交。保留他人的未跟踪报告和修改，不能使用 `git add .` 把它们顺带交付。提交前复查远端目标分支是否变化；推送只去用户指定分支，不擅自推 main。

“本地文件已写好”和“需求 AI 能在 Git 上读取”是两个状态。只有提交已进入其可访问分支，并给出完整 SHA/链接后，才能宣称远端交接完成。未发布时明确写“待提交/推送”，不要给不存在的提交链接。

每次交接必须给出：

- 仓库、实际目标分支、基准与结果 SHA，文档路径。
- 问题与改后行为、修改文件、批准决定及保持项。
- 命令、结果、环境、失败/跳过/未运行项。
- 截图或运行材料的实际路径和覆盖范围；没有就写待视觉验收。
- 尚未处理的问题、下一任务的输入与禁止顺带修改范围。

两个 AI 不应同时编辑同一工作区的同一批文件。需求文档先形成稳定版本，开发按该版本执行；开发中目标变化必须更新版本和差异。回退只处理本任务的具体修改或提交，不清空工作区、不回滚用户数据。

## 10. 后续实施顺序与阶段退出条件

当前历史已出现 P00–P09B 及多次修订提交；这只能证明有相关实现记录，不等于阶段均已人工验收。本轮先处理确定偏离、同步决策与文档，再逐模块按以下门槛推进。

| 后续工作 | 输入 | 退出条件 |
|---|---|---|
| 本轮修复复核 | 审计、差异、月度任务与单主题决定 | 行为定向验证、WebEngine 结果明确、用户查看首页 |
| P09A/B 复核 | 需求/日报/文档与数据库/SQL 已有代码 | 功能入口、分栏、长内容、表单与子窗对照规格；不凭提交名通过 |
| P09C 运维与接口 | 现有接口、日志、命令库调用链 | 捕获/SSH/命令行为等价，加载/错误/取消可验证 |
| P09D 模型与学习 | 聊天、Agent、学习权限与状态链 | 首字/流式/停止/目录/解锁等价，视觉统一 |
| P09E 工具与设置 | 证件、VIN、加解密、格式、设置 | 算法与选项保持，单主题兼容验证，子窗无遗漏 |
| P10 集成验收 | 前述功能清单与证据 | 22 叶子入口及公共/子窗口覆盖，构建与必要发布检查，用户视觉接受 |

每个模块先输出动作清单和设计差异，再开发。若当前源码已包含部分目标，应复用并验证，不重复推翻。每次只推进明确的一组页面，避免公共组件未稳定就铺开所有业务页。
