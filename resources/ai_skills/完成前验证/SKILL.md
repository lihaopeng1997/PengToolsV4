# 完成前验证

## 概述

没有验证就声称工作完成是不诚实，不是效率。

**核心原则：** 证据优先于断言，始终。

**违反这个规则的文字就是违反这个规则的精神。**

## 铁律

```
没有最新验证证据不做完成声明
```

如果你没有在这个消息中运行验证命令，你就不能声称它通过了。

## 门禁功能

```
在声称任何状态或表达满意之前：

1. 识别：什么命令证明这个声明？
2. 运行：执行完整命令（全新的、完整的）
3. 读取：完整输出，检查退出码，计数失败
4. 验证：输出确认声明了吗？
   - 如果否：用证据陈述实际状态
   - 如果是：带证据陈述声明
5. 然后：才能做声明

跳过任何步骤 = 说谎，不是验证
```

## 常见失败

| 声明 | 需要 | 不充分 |
|--------|------|--------|
| 测试通过 | 测试命令输出：0 失败 | 上次运行，"应该通过" |
| Linter 干净 | Linter 输出：0 错误 | 部分检查，推测 |
| 构建成功 | 构建命令：退出 0 | Linter 通过，日志看起来好 |
| Bug 修复 | 测试原始症状：通过 | 代码改了，假设修复 |
| 回归测试工作 | 红-绿循环验证 | 测试通过一次 |
| Agent 完成 | VCS diff 显示更改 | Agent 报告"成功" |
| 需求满足 | 逐行检查清单 | 测试通过 |

## 红牌 - 停下来

- 使用"应该"、"可能"、"看起来"
- 在验证之前表达满意（"好！"、"完美！"、"完成！"等）
- 在验证之前提交/推送/PR
- 信任 Agent 成功报告
- 依赖部分验证
- 认为"就这一次"
- 累了想结束工作
- **任何暗示成功但没有运行验证的措辞**

## 理性化预防

| 借口 | 现实 |
|--------|------|
| "现在应该工作了" | 运行验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "Agent 说成功" | 独立验证 |
| "我累了" | 疲惫不是借口 |
| "部分检查够了" | 部分什么都证明不了 |
| "换了词规则不适用" | 精神高于文字 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [见：34/34 通过] "所有测试通过"
❌ "现在应该通过了" / "看起来正确"
```

**回归测试（TDD 红-绿）：**
```
✅ 写 → 运行（通过）→ 还原修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ "我写了回归测试"（没有红-绿验证）
```

**构建：**
```
✅ [运行构建] [见：退出 0] "构建通过"
❌ "Linter 通过了"（linter 不检查编译）
```

**需求：**
```
✅ 重读计划 → 创建检查清单 → 验证每个 → 报告差距或完成
❌ "测试通过，阶段完成"
```

**Agent 委托：**
```
✅ Agent 报告成功 → 检查 VCS diff → 验证更改 → 报告实际状态
❌ 信任 Agent 报告
```

## 为什么这重要

从 24 个失败记忆中：
- 用户说"我不相信你"——信任被破坏
- 未定义函数被交付——会崩溃
- 缺少需求被交付——功能不完整
- 虚假完成浪费时间 → 重定向 → 返工
- 违反："诚实是核心价值。如果你说谎，你会被替换。"

## 何时应用

**总是在之前：**
- 任何成功/完成声明的变化
- 任何满意表达
- 任何关于工作状态的正面陈述
- 提交、PR 创建、任务完成
- 移动到下一个任务
- 派遣给 Agent

**规则适用于：**
- 确切短语
- 释义和同义词
- 成功的暗示
- 任何暗示完成/正确的沟通

## 底线

**验证没有捷径。**

运行命令。读取输出。然后才能声称结果。

这是不可协商的。
