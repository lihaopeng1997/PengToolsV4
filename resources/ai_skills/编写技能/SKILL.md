# 编写技能

## 概述

**编写技能就是将测试驱动开发应用于过程文档。**

你写测试用例（用子 Agent 的压力场景），看着它们失败（基线行为），写技能（文档），看着测试通过（Agent 合规），然后重构（关闭漏洞）。

**核心原则：** 如果你没有看着 Agent 在没有技能的情况下失败，你不知道技能教的是否正确。

**要求背景：** 在使用此技能之前，你必须理解 superpowers:测试驱动开发。那个技能定义了基本的红-绿-重构循环。这个技能将 TDD 适配到文档。

## 什么是技能？

**技能**是经过验证的技术、模式或工具的参考指南。技能帮助未来的 AI 实例找到并应用有效方法。

**技能是：** 可复用技术、模式、工具、参考指南

**技能不是：** 关于你如何一次解决问题 的叙述

## 技能的 TDD 映射

| TDD 概念 | 技能创建 |
|-------------|----------------|
| **测试用例** | 用子 Agent 的压力场景 |
| **生产代码** | 技能文档（SKILL.md） |
| **测试失败（RED）** | 没有技能时 Agent 违反规则（基线） |
| **测试通过（GREEN）** | 技能存在时 Agent 合规 |
| **重构** | 在保持合规的同时关闭漏洞 |
| **先写测试** | 在写技能之前运行基线场景 |
| **看着它失败** | 记录 Agent 使用的确切理性化 |
| **最少代码** | 写技能解决那些特定违规 |
| **看着它通过** | 验证 Agent 现在合规 |
| **重构循环** | 找新理性化 → 堵住 → 重新验证 |

整个技能创建过程遵循红-绿-重构。

## 何时创建技能

**创建当：**
- 技术对你来说不是直观明显的
- 你会在项目间参考这个
- 模式应用广泛（不是特定项目的）
- 其他人会受益

**不要创建：**
- 一次性解决方案
- 在其他地方有良好文档记录的标准实践
- 特定项目约定（放在 CLAUDE.md）
- 机械约束（如果可以用 regex/验证强制执行，就自动化——将判断保留给决策）

## 技能类型

### 技术
具有要遵循的步骤的具体方法（条件等待、溯源追踪）

### 模式
思考问题的方式（用标志展平、测试不变量）

### 参考
API 文档、语法指南、工具文档（办公文档）

## 目录结构

```
skills/
  skill-name/
    SKILL.md              # 主要参考（必需）
    supporting-file.*     # 仅在需要时
```

**扁平命名空间**——所有技能在一个可搜索命名空间

**分开文件用于：**
1. **重参考**（100+ 行）——API 文档、综合语法
2. **可复用工具**——脚本、工具、模板

**保持内联：**
- 原则和概念
- 代码模式（< 50 行）
- 其他一切

## SKILL.md 结构

**前言（YAML）：**
- 只支持两个字段：`name` 和 `description`
- 最多 1024 字符
- `name`：只使用字母、数字和连字符（无括号、特殊字符）
- `description`：第三人称，只描述何时使用（不是做什么）
  - 以 "Use when..." 开始，聚焦触发条件
  - 包含具体症状、情况、上下文
  - **绝不总结技能的过程或工作流**（见 CSO 部分了解原因）
  - 尽可能保持在 500 字符以下

```markdown
---
name: Skill-Name-With-Hyphens
description: Use when [specific triggering conditions and symptoms]
---

# Skill Name

## Overview
这是什么？1-2 句话核心原则。

## When to Use
[如果决策不明显，小内联流程图]

触发条件和用例的子弹列表
何时不使用

## Core Pattern (for techniques/patterns)
前后代码比较

## Quick Reference
用于扫描常见操作的表格或子弹

## Implementation
简单模式的内联代码
重参考的文件链接

## Common Mistakes
什么出错 + 修复

## Real-World Impact (optional)
具体结果
```

## Claude 搜索优化（CSO）

**发现的关键：** 未来 AI 需要找到你的技能

### 1. 丰富的描述字段

**目的：** AI 读取描述来决定为给定任务加载哪些技能。使它回答："我现在应该读这个技能吗？"

**格式：** 以 "Use when..." 开始，聚焦触发条件

**关键：描述 = 何时使用，不是技能做什么**

**为什么重要：** 测试揭示，当描述总结技能工作流时，AI 可能遵循描述而不是阅读完整技能内容。

```yaml
# ❌ 坏：总结工作流——AI 可能遵循这个而不是阅读技能
description: Use when executing plans - dispatches subagent per task with code review between tasks

# ❌ 坏：太多过程细节
description: Use for TDD - write test first, watch it fail, write minimal code, refactor

# ✅ 好：只触发条件，无工作流总结
description: Use when executing implementation plans with independent tasks in the current session
```

**内容：**
- 使用具体触发器、症状、情况来描述技能适用的信号
- 描述*问题*（竞态条件、不一致行为）而不是*语言特定症状*
- 保持触发器技术不可知，除非技能本身是技术特定的
- 如果技能是技术特定的，在触发器中明确说明
- 用第三人称写（注入系统提示）
- **绝不总结技能的过程或工作流**

### 2. 关键词覆盖

使用 AI 会搜索的词：
- 错误消息："Hook timed out"、"ENOTEMPTY"、"race condition"
- 症状："flaky"、"hanging"、"zombie"、"pollution"
- 同义词："timeout/hang/freeze"、"cleanup/teardown/afterEach"
- 工具：实际命令、库名、文件类型

### 3. 描述性命名

**使用主动语态，动词优先：**
- ✅ `creating-skills` 不是 `skill-creation`
- ✅ `condition-based-waiting` 不是 `async-test-helpers`

### 4. Token 效率（关键）

**问题：** getting-started 和频繁引用的技能加载到每个对话。每个 token 都很重要。

**目标字数：**
- getting-started 工作流：每个 < 150 词
- 频繁加载的技能：总共 < 200 词
- 其他技能：< 500 词（仍然要简洁）

**技术：**

**将细节移到工具帮助：**
```bash
# ❌ 坏：在 SKILL.md 中记录所有标志
search-conversations 支持 --text、--both、--after DATE、--before DATE、--limit N

# ✅ 好：参考 --help
search-conversations 支持多种模式和过滤器。运行 --help 获取详情。
```

**使用交叉引用：**
```markdown
# ❌ 坏：重复工作流细节
搜索时，用模板派遣子Agent...
[20 行重复指令]

# ✅ 好：引用其他技能
总是使用子Agent（50-100x 上下文节省）。必需：使用 [其他技能名] 获取工作流。
```

## 流程图使用

**仅用于：**
- 不明显的决策点
- 可能过早停止的过程循环
- "何时用 A vs B"决策

**绝不用于：**
- 参考材料 → 表格、列表
- 代码示例 → Markdown 块
- 线性指令 → 编号列表
- 没有语义意义的标签（step1、helper2）

## 代码示例

**一个优秀示例胜过许多平庸示例**

选择最相关的语言：
- 测试技术 → Python
- 系统调试 → Shell/Python
- 数据处理 → Python

**好示例：**
- 完整可运行
- 解释为什么的注释充分
- 来自真实场景
- 清晰展示模式
- 可直接适配（不是通用模板）

**不要：**
- 用 5+ 种语言实现
- 创建填空模板
- 写 contrived 示例

你擅长移植——一个好的示例就够了。

## 文件组织

### 自包含技能
```
defense-in-depth/
  SKILL.md    # 一切都内联
```
当：所有内容适合，不需要重参考

### 有可复用工具的技能
```
condition-based-waiting/
  SKILL.md    # 概述 + 模式
  example.py  # 可复用 helpers 适配
```
当：工具是可复用代码，不只是叙述

### 有重参考的技能
```
pptx/
  SKILL.md       # 概述 + 工作流
  pptxgenjs.md   # 600 行 API 参考
  ooxml.md       # 500 行 XML 结构
```
当：参考材料太大无法内联

## 铁律（与 TDD 相同）

```
没有失败测试就不写技能
```

这适用于新技能和现有技能的编辑。

写技能之前测试？删除它。重来。
编辑技能不测试？同样违规。

**没有例外：**
- 不是因为"简单添加"
- 不是因为"就加一节"
- 不是因为"文档更新"
- 不要保留未测试的更改作为"参考"
- 不要在运行测试时"改编"
- 删除就是删除

## 常见跳过测试的理性化

| 借口 | 现实 |
|--------|------|
| "技能明显清楚" | 对你清楚 ≠ 对其他 AI 清楚。测试它。 |
| "这只是参考" | 参考可能有空白、不清楚的部分。测试检索。 |
| "测试太过度" | 未测试技能有问题。总是测试。15 分钟测试节省数小时。 |
| "如果出问题再测试" | 问题 = AI 无法使用技能。部署前测试。 |
| "太乏味" | 测试比在生产中调试坏技能更不乏味。 |
| "我有信心它是好的" | 过度自信保证有问题。仍然测试。 |
| "学术审查够了" | 阅读 ≠ 使用。测试应用场景。 |
| "没时间测试" | 部署未测试技能浪费更多时间稍后修复。 |

**所有这些意味着：部署前测试。没有例外。**

## 用理性化加固技能

强制规则的技能（如 TDD）需要抵抗理性化。AI 很聪明，在压力下会找到漏洞。

### 明确关闭每个漏洞

不要只陈述规则——禁止具体变通方案：

```markdown
写代码在测试之前？删除它。重来。

**没有例外：**
- 不要保留它作为"参考"
- 不要在写测试时"改编"它
- 不要看它
- 删除就是删除
```

### 解决"精神 vs 文字"争论

尽早添加基本原则：

```markdown
**违反规则的文字就是违反规则的精神。**
```

这切断了一整类"我在遵循精神"的理性化。

### 构建理性化表

从基线测试中捕获理性化：

```markdown
| 借口 | 现实 |
|--------|------|
| "太简单不用测" | 简单代码也会坏。测试只需 30 秒。 |
| "我之后测" | 测试立即通过什么都证明不了。 |
```

### 创建红牌列表

让 AI 在理性化时容易自检：

```markdown
## 红牌 - 停下来重新开始

- 代码在测试之前
- "我已经手动测试过了"
- "之后测也能达到同样目的"
- "这是关于精神不是仪式"
- "这不一样因为……"

**所有这些意味着：删除代码。用 TDD 重来。**
```

## 红-绿-重构用于技能

遵循 TDD 循环：

### RED：写失败测试（基线）

在没有技能的情况下用子 Agent 运行压力场景。记录确切行为：
- 他们做了什么选择？
- 他们用了什么理性化（逐字）？
- 什么压力触发了违规？

这是"看着测试失败"——你必须看到 AI 自然做什么，然后再写技能。

### GREEN：写最少技能

写解决那些特定理性化的技能。不要为假设情况添加额外内容。

用技能运行相同场景。AI 现在应该合规。

### REFACTOR：关闭漏洞

AI 发现了新理性化？添加明确对策。重新测试直到无懈可击。

## 反模式

### ❌ 叙述示例
"在 2025-10-03 的会话中，我们发现空 projectDir 导致……"
**为什么坏：** 太特定，不可复用

### ❌ 多语言稀释
example-js.js、example-py.py、example-go.go
**为什么坏：** 质量平庸，维护负担

### ❌ 流程图中的代码
```dot
step1 [label="import fs"];
step2 [label="read file"];
```
**为什么坏：** 无法复制粘贴，难读

### ❌ 通用标签
helper1、helper2、step3、pattern4
**为什么坏：** 标签应该有语义意义

## 继续下一个技能之前停止

**写完任何技能后，你必须停下来完成部署过程。**

**不要：**
- 批量创建多个技能而不测试每个
- 在当前技能验证之前移动到下一个
- 因为"批量更高效"跳过测试

**部署检查清单对每个技能都是强制的。**

部署未测试技能 = 部署未测试代码。这是质量标准违规。

## 技能创建检查清单（TDD 适配）

**重要：使用 TodoWrite 为以下每个检查清单项目创建 todo。**

**RED 阶段 - 写失败测试：**
- [ ] 创建压力场景（ discipline 技能 3+ 组合压力）
- [ ] 在没有技能的情况下运行场景——逐字记录基线行为
- [ ] 识别理性化/失败中的模式

**GREEN 阶段 - 写最少技能：**
- [ ] 名称只使用字母、数字、连字符（无括号/特殊字符）
- [ ] YAML 前言只有 name 和 description（最多 1024 字符）
- [ ] Description 以 "Use when..." 开始并包含具体触发器/症状
- [ ] Description 用第三人称写
- [ ] 关键词贯穿全文（错误、症状、工具）
- [ ] 有清晰的核心原则概述
- [ ] 解决 RED 中识别的特定基线失败
- [ ] 代码内联或链接到单独文件
- [ ] 一个优秀示例（不是多语言）
- [ ] 用技能运行场景——验证 AI 现在合规

**REFACTOR 阶段 - 关闭漏洞：**
- [ ] 从测试中识别新的理性化
- [ ] 添加明确对策（如果是 discipline 技能）
- [ ] 从所有测试迭代构建理性化表
- [ ] 创建红牌列表
- [ ] 重新测试直到无懈可击

**质量检查：**
- [ ] 仅当决策不明显时才用小流程图
- [ ] 快速参考表格
- [ ] 常见错误部分
- [ ] 无叙述故事
- [ ] 仅在工具或重参考时才有支持文件

**部署：**
- [ ] 将技能提交到版本控制（SVN `svn commit`）
- [ ] 如果广泛有用，考虑贡献回 SVN 主干

## 发现工作流

未来 AI 如何找到你的技能：

1. **遇到问题**（"测试 flaky"）
2. **查找技能**（描述匹配）
3. **扫描概述**（这相关吗？）
4. **读取模式**（快速参考表）
5. **加载示例**（只在实施时）

**优化这个流程**——尽早放置可搜索术语，经常放。

## 底线

**创建技能就是为过程文档做 TDD。**

相同的铁律：没有失败测试就不写技能。
相同循环：RED（基线）→ GREEN（写技能）→ REFACTOR（关闭漏洞）。
相同好处：更好质量、更少意外、无懈可击结果。

如果你为代码遵循 TDD，为文档也遵循它。这是相同的纪律。
