# 系统化调试

## 概述

随机修复浪费时间并产生新 Bug。快速补丁掩盖潜在问题。

**核心原则：** 始终在尝试修复之前找到根本原因。症状修复是失败。

**违反这个过程的文字就是违反调试的精神。**

## 铁律

```
没有首先调查根本原因就不提修复方案
```

如果你没有完成第一阶段，你就不能提出修复方案。

## 何时使用

对任何技术问题使用：
- 测试失败
- 生产 Bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别在使用当：**
- 有时间压力时（紧急情况使人想猜测）
- "就一个快速修复"看起来很明显时
- 你已经尝试了多个修复方案时
- 之前的修复没有奏效时
- 你不完全理解问题时

**不要跳过当：**
- 问题看起来简单（简单 Bug 也有根本原因）
- 你赶时间（匆忙保证返工）
- 经理想要立即修复（系统化调试比胡乱尝试更快）

## 四个阶段

你必须完成每个阶段后才能进入下一个。

### 阶段 1: 根本原因调查

**在尝试任何修复之前：**

1. **仔细阅读错误消息**
   - 不要跳过错误或警告
   - 它们通常包含确切解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **一致地复现**
   - 你能可靠地触发它吗？
   - 确切步骤是什么？
   - 每次都发生吗？
   - 如果不能复现 → 收集更多数据，不要猜测

3. **检查最近变化**
   - 什么变化可能导致这个？
   - 版本差异（git diff / svn diff），最近提交
   - 新依赖、配置变化
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，为每个组件边界添加诊断工具：**
   ```
   对于每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置传播
     - 检查每层的状态

   运行一次收集证据，显示在哪里断开
   然后分析证据识别失败的组件
   然后调查该特定组件
   ```

5. **追踪数据流**

   **当错误在调用栈深处时：**

   参见本目录中的 `支持技术/溯源追踪.md` 获取完整的后向追踪技术。

   **快速版本：**
   - 坏值从哪里起源？
   - 谁用坏值调用了这个？
   - 继续追踪直到找到源头
   - 在源头修复，而不是症状

### 阶段 2: 模式分析

**在修复之前找到模式：**

1. **找工作的例子**
   - 在相同代码库中找到类似的工作代码
   - 什么工作了，与什么坏了类似？

2. **与参考对比**
   - 如果是实现模式，完整阅读参考实现
   - 不要略读——读每一行
   - 在应用之前完全理解模式

3. **识别差异**
   - 工作的和坏的区别是什么？
   - 列出每个差异，无论多小
   - 不要假设"那不可能有关系"

4. **理解依赖**
   - 这个还需要什么其他组件？
   - 什么设置、配置、环境？
   - 它做什么假设？

### 阶段 3: 假设和测试

**科学方法：**

1. **形成一个假设**
   - 清楚陈述："我认为 X 是根本原因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做最小的可能改变来测试假设
   - 一次一个变量
   - 不要同时修复多个东西

3. **验证后再继续**
   - 有效？是 → 阶段 4
   - 无效？形成新的假设
   - 不要在上面加更多修复

4. **当你不知道时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 做更多研究

### 阶段 4: 实施

**修复根本原因，而不是症状：**

1. **创建失败测试用例**
   - 最简单的可能复现
   - 如果可以，自动化测试
   - 如果没有框架，一次性测试脚本
   - 修复前必须有
   - 使用 `superpowers:测试驱动开发` 技能来写适当的失败测试

2. **实施单一修复**
   - 解决已识别的根本原因
   - 一次一个改变
   - 不要有"既然来了"的改进
   - 不要有捆绑的重构

3. **验证修复**
   - 测试现在通过了？
   - 没有其他测试被破坏？
   - 问题实际解决了？

4. **如果修复不奏效**
   - 停下来
   - 数数：你尝试了多少次修复？
   - 如果 < 3：返回阶段 1，用新信息重新分析
   - **如果 ≥ 3：停下来质疑架构（见下面第 5 步）**
   - 在架构讨论之前不要尝试第 4 次修复

5. **如果 3+ 次修复失败：质疑架构**

   **表明架构问题的模式：**
   - 每次修复都在不同地方揭示新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实施
   - 每次修复在其他地方产生新症状

   **停下来质疑基础：**
   - 这个模式根本上是合理的吗？
   - 我们是"纯粹靠惯性坚持"吗？
   - 我们应该重构架构还是继续修复症状？

   **在尝试更多修复之前与用户讨论**

   这不是假设失败——这是错误的架构。

## 红牌 - 停下来遵循过程

如果你发现自己想：
- "先快速修复，以后再调查"
- "就试试改 X 看看能不能工作"
- "加多个改变，运行测试"
- "跳过测试，我会手动验证"
- "可能是 X，让我修那个"
- "我不完全理解但这可能有效"
- "模式说 X 但我会不同地适应"
- "主要问题是：[列出修复方案而不调查]"
- 在追踪数据流之前提出解决方案
- **"再试一次修复"（已经尝试了 2+ 次）**
- **每次修复都在不同地方揭示新问题**

**所有这些意味着：停下来。返回阶段 1。**

**如果 3+ 次修复失败：** 质疑架构（见阶段 4.5）

## 用户的信号说明你做错了

**注意这些重定向：**
- "不是那样发生吗？"——你假设没有验证
- "这会告诉我们……？"——你应该已经添加了证据收集
- "停止猜测"——你在没有理解的情况下提出修复
- "仔细想这个"——质疑基础，不只是症状
- "我们卡住了？"（沮丧）——你的方法不工作

**看到这些时：** 停下来。返回阶段 1。

## 常见理性化

| 借口 | 现实 |
|--------|------|
| "问题简单，不需要过程" | 简单问题也有根本原因。过程对简单 Bug 也快。 |
| "紧急，没时间走过程" | 系统化调试比猜测-检查-胡乱尝试更快。 |
| "先试试这个，然后再调查" | 第一次修复设置了模式。从一开始就做对。 |
| "修复后确认有效再写测试" | 未测试的修复不会持久。测试优先证明它有效。 |
| "同时多个修复节省时间" | 无法隔离什么有效了。会造成新 Bug。 |
| "参考太长，我会适应模式" | 部分理解保证 Bug。完整阅读。 |
| "我看到问题了，让我修复" | 看到症状 ≠ 理解根本原因。 |
| "再试一次修复"（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|-------|---------------|----------------|
| **1. 根本原因** | 读错误、复现、检查变化、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 找工作例子、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 当过程揭示"没有根本原因"时

如果系统调查表明问题确实是环境的、时间依赖的或外部的：

1. 你已经完成了过程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误消息）
4. 为将来调查添加监控/日志

**但是：** 95% 的"没有根本原因"案例是调查不完整。

## 支持技术

这些技术是系统化调试的一部分，在本目录中可用：

- **`支持技术/溯源追踪.md`** - 通过调用栈向后追踪 Bug 找到原始触发器
- **`支持技术/纵深防御.md`** - 找到根本原因后在多层添加验证
- **`支持技术/条件等待.md`** - 用条件轮询替换任意超时

**相关技能：**
- **superpowers:测试驱动开发** - 创建失败测试用例（阶段 4，步骤 1）
- **superpowers:完成前验证** - 在声称成功之前验证修复有效

## 实际影响

从调试会话：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时胡乱尝试
- 首次修复率：95% vs 40%
- 引入新 Bug：接近零 vs 常见
