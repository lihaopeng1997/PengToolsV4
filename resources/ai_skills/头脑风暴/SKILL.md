# 将想法头脑风暴为设计方案

## 概述

通过自然的协作对话，将想法转化为完整的设计方案和规范。

首先了解当前项目背景，然后一次提出一个问题来细化想法。一旦理解要构建的内容，将设计方案分成小节（200-300 字）呈现，并在每节之后检查是否正确。

## 流程

**理解想法：**
- 先查看当前项目状态（文件、文档、最近提交）
- 一次提出一个问题来细化想法
- 尽量用选择题，开放式也可以
- 每条消息只问一个问题——如果某个主题需要更多探索，拆成多个问题
- 聚焦于理解：目的、约束、成功标准

**探索方案：**
- 提出 2-3 个不同方案并说明权衡
- 以对话方式呈现选项，说明推荐方案及理由
- 先给出推荐方案并解释原因

**呈现设计：**
- 一旦确信理解了要构建的内容，就开始呈现设计
- 拆成 200-300 字的小节
- 每节之后询问是否看起来正确
- 覆盖：架构、组件、数据流、错误处理、测试
- 如果有不明白的地方，准备好回头澄清

## 设计之后

**文档：**
- 将已验证的设计写入 `docs/plans/YYYY-MM-DD-<topic>-design.md`
- 提交设计文档到 git

**实施（如果继续）：**
- 询问："准备好开始实施了吗？"
- 使用 `superpowers:撰写计划` 创建详细实施计划

## 关键原则

- **一次只问一个问题**——不要用多个问题淹没用户
- **尽量用选择题**——比开放式问题更容易回答
- **YAGNI 严格遵循**——从所有设计中移除不必要的功能
- **探索替代方案**——在确定之前总是提出 2-3 个方案
- **增量验证**——分节呈现设计，验证每一节
- **保持灵活**——当有不明白的地方时，回头澄清
